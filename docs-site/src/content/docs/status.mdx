terragucci is being built. The rest of this site describes it finished, so this page is the one to read before relying on a feature. It is authoritative over every other page and the README.

## What you can run today

| Piece | What works |
|---|---|
| The tutorial's example | `just example up` boots 15 roots on a local Forgejo and applies them to floci, with the scenarios ready to open as pull requests |
| The check stage | format and validate on every pull request, failing by file name; `validate` diagnostics print with file and range, `choudoufu live-check` runs for a choudoufu repo, and a configured policy's tests run. Built; on the stack, a validate error, a failing policy test and a choudoufu live-check refusal each fail `tf-check` with the cause in its log (`check-diagnostics`) |
| `npx terragucci init` | finds a repo's roots, binary and forge, and writes its pipeline for GitHub, GitLab or Forgejo; the pipeline checks every root and applies them in dependency order on the main branch |
| Terragrunt repos | `init` notices Terragrunt, takes the units from `terragrunt find`, and writes a pipeline that checks with `hcl fmt` and `hcl validate`, plans the units a pull request reaches and applies a wave at a time with one `run --all`. A unit whose plan would read `mock_outputs` waits for its upstream instead of planning, and tips name mocks that can reach apply. Roles can follow unit paths. `just example-terragrunt up` boots the Terragrunt example: 15 units on the local Forgejo, applied to floci |
| CI images | one per toolchain (OpenTofu, Terraform, Terragrunt, choudoufu), built and checked on amd64 and arm64; published to ghcr.io/intentius, and `init` pins each by digest. `init` writes a choudoufu repo's pipeline in the choudoufu image; CDK Terrain has no image yet, so `init` refuses `binary: cdktn` |
| The npm package | `@intentius/terragucci` on npm (`npm i -D @intentius/terragucci`), one bundled file with no dependencies, published with provenance |
| Dashboards and alert rules | `dashboards:` in `terragucci.yml` makes `init` and `reconcile` write seven dashboards, the SLO and pipeline alert rules, and Grafana's provisioning files, declared with chant's grafana and prometheus lexicons; the observability profile adds Grafana and Tempo |
| `terragucci stage tf-plan` | plans the roots a pull request reaches, and the roots that read their state, planning the roots of each dependency layer at once (up to `parallelism`, in a stable order), and writes the plan report: JSON, HTML, the pull-request note and GitLab's counts, with each root's full plan beside it, sensitive values redacted; with `reports.bucket`, copies it to the bucket and updates the index. The generated pipeline's plan job runs it on every pull request, posts its note and keeps it as the job's artifact |
| Traces and metrics | with an OTLP endpoint set, `tf-plan` sends one trace per run, with a span per wave, root and binary run, and OpenTofu's own spans inside it; and its metrics, read from the report. Terraform's own spans land in a separate trace, tagged with the run's trace and span ids so a query finds them |
| Run timings | `tf-plan` and `tf-drift` collect each root's plan spans on a loopback OTLP receiver and the report lists the slowest roots and, per root, the slowest resources, provider calls, provider start-up and lock waits, or choudoufu's summed spans in aggregate mode; a root whose binary sent nothing per resource says so. The binary's spans are passed on to the collector when an endpoint is set. A Terragrunt unit's time comes from Terragrunt's run report (slowest first), and its plan's spans reach the receiver through a `TG_TF_PATH` wrapper; with OpenTofu, which stops above the resource, that gives provider start-up and lock waits but nothing per resource. A Terragrunt unit's plan waits up to five minutes for the state lock, as a wave's plan does. A `tf-apply` wave writes its own report with each root's plan and apply times and lock waits. A lock wait on S3 with `use_lockfile` is shown on the stack for a choudoufu plan (`lock-wait`) |
| Affected-only plans | a pull request plans only the roots its change reaches, and the roots that read their state; the rest are left alone |
| One grouped plan note | one note on the pull request or merge request for every plan across the roots: identical changes folded into a group, destroys, replacements and outliers named on their own and open, each root linked to its full plan |
| Gated waves | `tf-apply` runs one job per wave, canary first, each wave planned after the one before it applied and behind a gate bound to its set digest. Under the default `on-destroy` policy a wave waits when its plans destroy or replace something, and `always` and `never` are the other two. A wave whose plans changed after approval applies nothing and names the roots that moved |
| Sealed approvals | on by default: a wave counts an approval only when it is sealed by a key in `.chant/allowed_signers` on the default branch. You approve with `chant approve tf-apply wave-N --sign`; the waiting job prints the command, and an MCP session cannot approve a wave |
| The fresh-estate plan | on an estate with no state yet, the plan holds back a root whose upstream is unapplied, and says so, instead of planning against placeholder values |
| `tf-drift` | one plan sweep across every root on a schedule, reported as one grouped issue; Terragrunt units are swept too |
| Module publishing and rollouts | `tf-publish` releases changed modules as OCI artifacts or git tags, and `tf-rollout` moves the pins one wave at a time, one pull request per wave, across roots and repos |
| `terragucci respond` | the default response to each pipeline event: the refused-wave diff, apply-failure triage, drift codified as a pull request with import blocks, one pull request per tip, `fmt` on a pull request's branch, and module release notes; `respond` in the config picks each one, and `agent` is checked but no generated job runs an agent yet |
| `terragucci.yml` and `terragucci reconcile` | one config for one repo or many; from a control repo, a pull request in each project that changes |
| The local validation stack | floci with Forgejo, GitHub (`act` and a mock API) or GitLab, each with its claims on the [validation page](/terragucci/reference/validation/); the fountain profile runs the example's `tf-apply` as a turn on a fountain steward, started by the forge job (the `steward` claim) |

## What the checks show

Each feature on this site has one check, run against the [tutorial's example](/terragucci/tutorial/) on a local Forgejo. A check that passes has also been broken on purpose, and it failed then.

## Still being built

| Feature | Status |
|---|---|
| Terragrunt explicit stacks (`terragrunt.stack.hcl`) | in development |
| A fountain steward started by a pull request | planned after launch |
| An apply comment command | built: `/terragucci apply [wave-<n>]` on a merged pull request re-runs `tf-apply` from its merge commit on GitHub and Forgejo, approving nothing, and a refused or failed wave gets the responses a push's wave gets; on GitHub it and a push's waves wait in one apply group with `queue: max`, so neither cancels the other, and a push's wave stands down once the branch moved past it; its claim `comment-apply` passes |
| A re-plan comment command | built: `/terragucci plan`, with or without a root, re-plans a pull request on GitHub and Forgejo and never applies, and a root the change does not reach is answered as not affected; its claims `comment-plan` and `comment-not-affected` pass |
| A `/terragucci agent <ask>` comment command | built: with `agent.comment` set, on GitHub and Forgejo, a coding agent (Claude Code by default) changes the pull request in a job with no cloud credentials, and a second job pushes its change to the pull request's branch unless it touches CI files, `terragucci.yml`, `.chant/`, the policy directory, `CODEOWNERS`, agent instruction files or `.gitattributes` and `.gitmodules`; its claim `comment-agent` passes |
| Links down from every view: the note to the bucket's report with `reports.url`, the report to its trace with `telemetry.trace_url`, the trace and the Runs and Estate dashboards back to the report and the index, index rows to the commit, pull request and job | built; its smoke claim (`drill-down`) passes |
| Opt-in policy checks with conftest or OPA, read from the base branch for a pull request (a `terragucci.ts` config included), failing `tf-plan` and refusing a `tf-apply` wave | built: both engines count `deny`, `violation` and `deny_*` and show `warn` without failing, `report.json` carries each root's verdict as `policy` and keeps a denied root's changes, and `input: hcp` runs an HCP Terraform policy set; its smoke claims (`policy`, `policy-wave`) pass |
| Typed decisions (`decide`): a mismatched pull-request description, drift attribution and version-bump suggestions | built: the `terragucci-decide` image and the client, the mismatched-description check (`respond.description`), drift attribution (`respond.drift: attribute`) and version-bump suggestions (`respond.version-bump: suggest`); the generated pipeline gives the drift job the service's key, the scheduled `tf-drift` run itself attributes drift of plain roots in its issue, and a `version-bump` job runs the suggestion after the apply; `report.json` carries the description check's decision as `intent`; the audit-log step reads CloudTrail only; none of the three has a recorded smoke claim yet |
| GCP and Azure credentials over OIDC | built: `oidc.gcp` writes a Workload Identity Federation `external_account` file and `oidc.azure` sets the `ARM_*` OIDC variables in the plan, apply and drift jobs on GitHub, GitLab and Forgejo; its smoke claim (`oidc-clouds`) runs the credential step against a stand-in token endpoint and passes, and no job has signed in to GCP or Azure on the stack, which serves neither cloud |

The tutorial grows a page each time one of these passes its check.
