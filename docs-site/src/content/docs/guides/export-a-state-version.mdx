## What you end up with

One version of a root's state in a file on your machine that only you can read. A record on [`chant/lifecycle`](/terragucci/concepts/glossary/#chantlifecycle) names who exported which root and version, and who approved it. The [audit trail](/terragucci/reference/audit-trail/) lists it as a `state-export` entry.

The state goes to the person who runs the command and nowhere else. It never goes to the reports bucket, and no job writes it as an artifact: a job's artifact is readable by everyone with read access to the repo for as long as the forge keeps it, which on a public repo is everyone, and a state holds every secret its resources hold. Run on your machine, the state reaches only someone whose own cloud identity can already read the bucket. What terragucci adds is the approval by someone else and the record.

## Before you start

| You need | Why |
|---|---|
| A root with an `s3` backend in a bucket with versioning on | the export reads a version by its id; [Find the state version an apply left](/terragucci/guides/find-a-state-version/) turns versioning on and lists the ids |
| Your own cloud identity that can read the state object | the command runs on your machine with your credentials |
| A checkout whose `origin` you can push to | the request and the record go to `chant/lifecycle` |
| Someone else to approve | an approval by the person who asked does not count |

The command refuses Terragrunt units and roots with a `cloud` block. A `local` backend, or a bucket that keeps no versions, has no version id to export.

## Steps

<Steps>

1. Ask for the version. Take its id from the estate page's State versions section, or leave `--version` out for the bucket's current version:

   ```bash
   terragucci state export envs/dev/app --version 3HL4kqtJlcpXroDTDmJ.rmSpXd3dIbrHY
   ```

   It reads the version's metadata and never its body. Then it records the request and exits 3:

   ```text
   state export: alice asks for envs/dev/app's state, s3://acme-state/dev/app.tfstate version 3HL4kqtJlcpXroDTDmJ.rmSpXd3dIbrHY; request sha256:5e0b...
   someone other than you approves it with:
     chant approve tf-state-export envs/dev/app --plan sha256:5e0b...
   then run this command again to download it.
   ```

   The request names you by git's `user.name`, or by `--actor`.

2. Someone else approves the request with the [chant](/terragucci/concepts/glossary/#chant) command it printed. Under `approval: sealed` the approval needs a seal (`--sign`) from a key the signers file lists.

3. Run the same command again. It downloads the version and records the export in `_gates/tf-state-export/done.jsonl`. Only then does it write the file:

   ```text
   state export: wrote /tmp/terragucci-export-Xb3k/envs_dev_app.3HL4kqtJlcpXroDTDmJ.rmSpXd3dIbrHY.tfstate: envs/dev/app's state, s3://acme-state/dev/app.tfstate version 3HL4kqtJlcpXroDTDmJ.rmSpXd3dIbrHY, approved by bob
   ```

   The file is mode 0600 in a new directory of its own. `--out <file>` names another place outside the repo; a path inside the repo is refused, so the state is never committed by accident. When the record cannot be pushed, nothing is written.

4. Delete the file when you are done with it.

</Steps>

A request exports once. To export again, run the command again: it records a new request for a new approval.

## In the audit trail

`terragucci audit` turns the request into an `approval-requested` entry and the approval into an `approval` entry. The export is a `state-export` entry: `who` is the person who exported and `what` the root. Its `detail` holds the location and the version id, who approved it, and the digest of the file, never its contents.
