## Result

A waiting wave's Slack message has an Approve and a Decline button. A Teams card gives the approving reply, `@terragucci approve wave-2 <digest>`, since Teams sends card buttons only to a registered bot. Clicks and replies go to `terragucci relay`, which you run in your own cloud; terragucci hosts nothing.

| A click by | Under `approval: ledger` or `pr-review` | Under `approval: sealed` |
|---|---|---|
| a chat user the signers file lists beside their principal | the relay records an approval of the digest the message showed, as that principal and marked relayed, and says so in the thread; the resume job applies the wave | refused: only the approver's own key seals an approval, so they run `terragucci approve --sign` |
| a chat user no line lists | refused in the thread; nothing is recorded | the same |
| anyone, after the plans moved | refused, naming the digest waiting now; nothing is recorded | the same |

Decline records nothing; the relay names who declined in the thread, and the wave waits until someone approves its plans.

## Prerequisites

| You need | Why |
|---|---|
| [Chat notices](/terragucci/guides/notify-a-chat-channel/) for the channel | the buttons go on those messages |
| [`apply.resume`](/terragucci/reference/pipeline/#resume-after-an-approval) | the relay starts no job, so the resume job applies the wave once the approval stands |
| A signers file, `.chant/allowed_signers`, on the default branch | the relay maps a chat user to a principal there |
| A place to run a container, or a function | the relay runs in your cloud |

## Steps

<Steps>

1. Add each approver's chat ids beside the principal on their line of `.chant/allowed_signers`, then merge the change. The relay reads the file on the default branch for every click.

   ```text
   alice@acme.com,slack:T0123ABCD/U0456EFGH,teams:6f1c2d0e-1a2b-4c3d-8e9f-0a1b2c3d4e5f ssh-ed25519 AAAAC3Nz...
   ```

   | Chat | The id | Where to find it |
   |---|---|---|
   | Slack | `slack:<team id>/<user id>` | the user's profile, Copy member ID; the workspace's team id is in its settings |
   | Teams | `teams:<Entra object id>` | the user's Object ID in Microsoft Entra |

   The approval records the line's first principal that is not a chat id. A chat id listed on two people's lines maps to neither.

2. Make the relay's token. It is approve-only: the relay refuses to start with a token that can do more than read the repo and push [`chant/lifecycle`](/terragucci/concepts/glossary/#chantlifecycle).

   <Tabs syncKey="forge">
     <TabItem label="GitHub">
       A fine-grained token for this repo alone, with Contents: Read and write and nothing else, from an account that does not administer the repo. The relay refuses a classic token, and the default branch must be protected.
     </TabItem>
     <TabItem label="GitLab">
       A project access token with the Developer role and the `write_repository` and `read_api` scopes. The default branch must be protected with push allowed to Maintainers or no one, and `chant/lifecycle` protected with push for Developers.
     </TabItem>
     <TabItem label="Forgejo">
       A user with write access to the repo, and a token of theirs scoped `write:repository` and `read:user`. Protect the default branch so that user may not push to it.
     </TabItem>
   </Tabs>

3. Set up the chat side.

   <Tabs syncKey="chat">
     <TabItem label="Slack">
       Turn on Interactivity in the Slack app that holds the channel's incoming webhook, and set its Request URL to `<relay address>/slack`. Copy the app's Signing Secret.
     </TabItem>
     <TabItem label="Teams">
       Add an outgoing webhook named `terragucci` to the team, with `<relay address>/teams` as its callback URL. Teams shows its security token once; copy it.
     </TabItem>
   </Tabs>

4. Run the relay. It reads its settings from [its environment](/terragucci/reference/environment/#the-relay).

   <Tabs syncKey="relay">
     <TabItem label="Container">
       Any container platform, such as ECS, Cloud Run, Azure Container Apps or Kubernetes, behind HTTPS:

       ```bash
       docker run -p 8080:8080 \
         -e TERRAGUCCI_RELAY_REPO=https://github.com/acme/infra.git \
         -e TERRAGUCCI_RELAY_TOKEN -e SLACK_SIGNING_SECRET -e TEAMS_WEBHOOK_SECRET \
         ghcr.io/intentius/terragucci-tofu:<the tag init names> terragucci relay
       ```
     </TabItem>
     <TabItem label="Function">
       An AWS Lambda function built from a container image and reached through a function URL. The [Lambda Web Adapter](https://github.com/aws/aws-lambda-web-adapter) 1.1.0 extension passes each request to the same server, once `/healthz` answers:

       ```dockerfile
       FROM ghcr.io/intentius/terragucci-tofu:<the tag init names>
       COPY --from=public.ecr.aws/awsguru/aws-lambda-adapter:1.1.0 /lambda-adapter /opt/extensions/lambda-adapter
       ENV PORT=8080
       ENV AWS_LWA_READINESS_CHECK_PATH=/healthz
       CMD ["terragucci", "relay"]
       ```

       The adapter reads `PORT` when `AWS_LWA_PORT` is unset, and the relay serves on it. Give the function a timeout of 30 seconds or more: each cold start fetches the repo before the first request.

       Keep the token and the secrets in Secrets Manager and pass them to the function's environment.
     </TabItem>
   </Tabs>

   The startup log names the repo and default branch, then the user the relay pushes as. A token that can do more than approve stops the relay there, and the log gives the reason.

5. Set `notify.relay` in `terragucci.yml` and regenerate the pipeline, then merge:

   ```yaml
   apply:
     resume: 5
   notify:
     slack: SLACK_WEBHOOK_URL
     relay: terragucci
   ```

   ```bash
   npx terragucci init
   ```

   `relay` is the outgoing webhook's name in Teams, not a secret. The next waiting wave's message carries the buttons.

</Steps>

## Relay checks

| Check | Refused when |
|---|---|
| The request's signature: Slack's signing secret over the timestamp and body, or the Teams outgoing webhook's HMAC over the body | it does not verify, or a Slack request is more than five minutes old (401) |
| The chat user | no line of the signers file on the default branch lists them |
| The mode | the default branch's `approval` is `sealed` |
| The digest | no wave waits for the digest the button or reply names |

Slack waits three seconds for the relay to answer a click. If fetching the repo and pushing the approval take longer, Slack shows a timeout, but the thread reply still says what was recorded.

The approval line carries `relayedBy` and `via: slack` or `via: teams`, and the [audit trail](/terragucci/reference/audit-trail/) shows who relayed it. The [threat model](/terragucci/reference/threat-model/#the-chat-relay) says what the relay is trusted with.

## A gate that asks a decision point

With `apply.point` set, every wave gate asks a chant [decision point](https://intentius.io/chant/guide/ops/#a-gate-that-asks-a-decision-point) in your workspace instead of waiting for an approval. The point's deciders and quorum decide, and Approve in chat answers its question.

```yaml
approval: ledger
apply:
  point: prod-apply
```

The point is declared in the workspace's points file, and must declare `gate.planDigest`, so each wave's plans are their own question:

```json
{
  "points": {
    "prod-apply": {
      "title": "Apply this wave's plans",
      "question": { "type": "noul", "instructions": "Should these plans be applied?", "criteria": { "true": "Apply them.", "false": "Do not apply them." } },
      "inputs": { "gate.component": "the op", "gate.name": "the wave's gate", "gate.planDigest": "the plans the gate binds" },
      "deciders": [{ "kind": "quorum", "count": 2, "roles": ["maintainer"] }]
    }
  }
}
```

| Step | What happens |
|---|---|
| The wave reaches its gate | it asks the point with `gate.component` `tf-apply`, `gate.name` `wave-<k>` and `gate.planDigest`, keeps the question on `chant/lifecycle`, and waits (exit 3), printing `chant workspace points answer <id> --answer true --by <name>` |
| Someone clicks Approve | the relay answers the question yes as the clicker's principal, with `--relayed-by` the relay, from the default branch's tip. The relay never counts toward the quorum |
| The clicker holds the `agent` role in `.chant/trust.json` at base | not counted; with too few people the relay replies `quorum-not-met` and nothing is answered |
| An agent answers over MCP or ACP | counted for nobody, and refused for a wave gate, whose pending fact is marked never over MCP |
| The wave's job runs again | the answer passes the gate: the wave records a resolution that cites the answer record, then applies. Any other answer applies nothing (exit 4) |

`chant workspace points` lists the question and its answer, with who answered and who relayed it. `terragucci approve` does not pass a gate that asks a point. The resume job does not start the wave on an answer: run its job again, or comment `/terragucci apply`.
