## What you end up with

After each `tf-apply` wave, the version id of each root's state, next to the run that wrote it. When a state goes wrong you know which version to restore, and which commit and wave wrote the one after it.

| Where | What it holds |
|---|---|
| the wave's log | one line per root: where its state is and its version id |
| the wave's `report.json` | `roots[].state`, for each root that applied or had nothing to apply |
| the project's `states.json` in the reports bucket | each root's newest 20 versions, each with its commit, wave and report |
| the estate page | a State versions section, per project and root, newest first |
| the [audit trail](/terragucci/reference/audit-trail/) | `detail.state_versions` on the wave's `apply` entry |

terragucci reads the state object's metadata with an S3 `HEAD` request. It never reads, copies or stores a state's contents.

## Before you start

| You need | Why |
|---|---|
| Roots with an `s3` backend, on AWS S3 or an S3-compatible store | the version id is S3's `x-amz-version-id` |
| [Reports in a bucket](/terragucci/guides/keep-reports-in-a-bucket/) | `states.json` and the estate page live there |
| The [estate page](/terragucci/guides/see-every-project/), to see the list | the page reads `states.json` |

A Terragrunt unit is listed as a root is. Its working directory is in Terragrunt's cache, so terragucci reads its backend from its evaluated `remote_state` block (`terragrunt render --json`).

Other roots are still listed, with what terragucci knows:

| Root | Listed as |
|---|---|
| a bucket with versioning off | versions are off: S3 keeps only the latest state |
| a `local` backend | versions are off |
| any other backend (`gcs`, `azurerm`, `http` and so on) | the backend's type, versions unknown |
| a Terragrunt unit with no `remote_state` block that runs from Terragrunt's cache | versions unknown, naming why |

## Steps

<Steps>

1. Turn on versioning for the bucket that holds your state:

   ```bash
   aws s3api put-bucket-versioning --bucket acme-state --versioning-configuration Status=Enabled
   ```

   S3 then keeps each version of every state object until a lifecycle rule expires it. A rule that expires noncurrent versions after 90 days keeps the list short and the bill small.

2. Check the apply job can read the state object's metadata. A `HEAD` request needs `s3:GetObject` on the state's key, which the apply role already holds to run the backend. When the backend's configuration names static keys (`access_key`, `secret_key`), terragucci signs with those. A role the backend assumes itself (`assume_role`) is not assumed: if the job's own identity may not read the object, the root is listed with versions unknown and the reason.

3. Let a wave apply. Each root that applied, or had nothing to apply, gets a line in the log:

   ```text
   envs/dev/platform: state s3://acme-state/envs/dev/platform.tfstate version 3HL4kqtJlcpXroDTDmJ.rmSpXd3dIbrHY
   ```

   A bucket with versioning off prints `versions off` and why. A version that cannot be read never fails the wave.

4. Open the estate page. Run `terragucci estate` (or let its scheduled job run) and open the link it prints. The State versions section lists each root's versions, newest first, each linked to the wave's report that wrote it. A root whose bucket keeps no versions says versions are off.

</Steps>

## Go back to a version

Restoring a state version is a state write outside the gate, so take it through review like any other change. With the version id from the page:

```bash
aws s3api get-object --bucket acme-state --key envs/dev/platform.tfstate \
  --version-id 3HL4kqtJlcpXroDTDmJ.rmSpXd3dIbrHY restore.tfstate
tofu -chdir=envs/dev/platform state push -force restore.tfstate
tofu -chdir=envs/dev/platform plan
```

`state push` takes the backend's lock while it writes. The older state does not name resources created after it. The plan shows them as creates, and applying it would make a second copy of each. Import them, or remove them from the cloud, before the next wave applies the root.
