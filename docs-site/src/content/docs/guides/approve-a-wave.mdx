## What you end up with

One wave applied, with an approval recorded in your repo that names the exact plans you read.

## Before you start

| You need | Detail |
|---|---|
| A wave that ran | After a merge, or from `/terragucci apply` on an open pull request when [`apply.when`](/terragucci/reference/config/#apply-before-merge) is `pull-request`. |
| A gate | `gate` set to `on-destroy` (the default) or `always`. With `never`, no wave waits ([Gate policy](/terragucci/reference/stages/#gate-policy)). |
| [chant](/terragucci/concepts/glossary/#chant) | `npm i -D @intentius/chant @intentius/terragucci`, where you approve. |
| Write access | `chant approve` pushes a commit to `chant/lifecycle` with your own git credentials. |
| Under `approval: sealed` only | An ssh key of yours in `.chant/allowed_signers` on the default branch ([setup](#set-up-the-signers-file), once per repo). |
| To be a person | Nothing signs off for you. |

## Approval modes

`approval` in `terragucci.yml` decides which approvals count. Every mode binds the wave's set digest: an approval of other plans is refused as changed.

| Mode | Counts | Setup | What it proves |
|---|---|---|---|
| `ledger` (default) | any `chant approve` of the digest on `chant/lifecycle`, signed or not | none | someone with push access to `chant/lifecycle` approved these exact plans. Anyone who can push there can write an approval in anyone's name: it binds the plans, not the person. |
| `pr-review` | the merged pull request's approval of its head, by a reviewer other than its author with write access, when the wave plans what the review saw; and any `chant approve` of the digest, as under `ledger` | on GitHub or Forgejo, optionally require `terragucci/approval` in branch protection; on GitLab, an approval rule | a writer other than the author approved the head whose plans these are. An approval by the user the pipeline's token acts as never counts. A `chant approve` still binds the plans, not the person. |
| `sealed` | only an approval sealed with `--sign` by a key the signers file lists for its approver | a [signers file](#set-up-the-signers-file); `init` lists each wave under [`identity.gates`](/terragucci/concepts/glossary/#identitygates) | a listed person approved these exact plans |

A wave reads the mode at base, like the signers file ([Which commit the rule is read from](#which-commit-the-rule-is-read-from)), and `terragucci config check` prints the mode in force and its source.

| `terragucci.yml` | Mode in force |
|---|---|
| sets `approval` | that mode |
| sets none, and [`chant.workspace.json`](/terragucci/concepts/glossary/#chantworkspacejson) lists gates under `identity.gates` | `sealed`; set `approval: sealed` to say so, or `approval: ledger` and run `terragucci init` to drop the gates |
| sets none, and no gates are listed | `ledger` |

## Approve by review (`approval: pr-review`)

Every forge. GitLab's merge request approvals name no commit, so there an approval counts only when it came after the merge request's latest push.

<Steps>

1. Open the pull request's plan note. Its waves table has each wave's digest of its changes and whether the gate will hold it; the note keeps the digests for the apply to compare.

2. Read the plans, then approve the pull request on its head.

   <Tabs syncKey="forge">
     <TabItem label="GitHub">
       Files changed > Review changes > Approve, from an account with write access.
     </TabItem>
     <TabItem label="GitLab">
       Approve on the merge request, as a member with the Developer role or higher, after its last push. An approval the author gives, or one withdrawn later, never counts.
     </TabItem>
     <TabItem label="Forgejo">
       Files changed > Review > Approve. Forgejo marks the review official when you have write access, and only an official one counts.
     </TabItem>
   </Tabs>

   The author's own approval never counts. A push after your review needs a fresh one, since a review counts only on the commit it names (on GitLab, only after the latest push), and a latest review that asks for changes holds every wave back.

3. Keep unreviewed changes from merging.

   | Forge | Require |
   |---|---|
   | GitHub | `terragucci/approval` under Settings > Branches (or Rules) > the default branch > Require status checks. It is pending while a wave the gate will hold has no approving review of the head. |
   | Forgejo | `terragucci/approval` under Settings > Branches > the default branch's rule > Status check patterns, with the same meaning. |
   | GitLab | an approval rule under Settings > Merge requests (GitLab Premium and Ultimate); the pipeline posts no `terragucci/approval` there. |

4. Merge. Each gated wave plans the merge commit and compares the digest of its changes with the one the note recorded for the reviewed head.

   | Outcome | Wave |
   |---|---|
   | same digest | records the approval on `chant/lifecycle` (`via: pr-review`, the pull request, its head and the reviewers) and applies |
   | another digest (the plans moved after the review) | applies nothing, exits 4 and prints the `chant approve` command for the new digest |
   | no row for the wave in the note, no approving review, or a direct push | waits for a `chant approve`, as under `ledger` |

5. A wave that waits for want of a review can still take one. On GitHub and Forgejo, approve the merged pull request on its head; on GitLab, approve the merge request while it is open, since GitLab takes no approval after the merge. Then run the wave again ([step 4 below](#approve-with-chant)): it finds the review and applies. With [`notify`](/terragucci/guides/notify-a-chat-channel/#approve-from-the-message-by-review) set, the waiting wave's chat message links the review page.

</Steps>

## Approve with chant

<Steps>

1. Find the waiting wave and its command.

   | Where | What it gives |
   |---|---|
   | the pull request's plan note, before the merge | each wave the gate will hold, with `chant approve tf-apply wave-<k> --plan <digest>`; after the merge the wave asks for that digest unless its plans moved |
   | `terragucci/apply` on the commit | the waiting wave's command, as the status's description: pending on GitHub and Forgejo, failed on GitLab, which cannot move a running status back to pending |
   | the job's log, or a comment's reply | the same command; the job exits with code 3 |

   In the example, `just example change destroy` opens a destroy and `just example merge destroy` merges it.

   <Shot step="wave-waiting" view="pull" alt="The destroy pull request in Forgejo with terragucci's plan note, which lists the destroy at the top" optional />
   <Shot step="wave-waiting" view="log" alt="The apply job's log: the wave waits, exit code 3, and the chant approve command with the plan digest" optional />
   <Captured step="wave-waiting" cmd="just example merge destroy" optional />

   On GitHub, the waiting wave's job ends with a red cross, exit code 3:

   <Shot step="github" view="waiting" alt="A GitHub Actions run on main after a destroy merged: check and apply-wave-1 to apply-wave-3 green, apply-wave-4 stopped with a red cross while it waits for an approval" />

2. Read what the wave will do.

   The wave waits because a plan destroys or replaces something, or because `gate` is `always`. Destroys and replacements are never grouped, so they sit at the top of the report. Read each one.

3. Approve it from a checkout of the repo.

   <Tabs syncKey="approval">
     <TabItem label="ledger (default) or pr-review">
       ```bash
       npx terragucci approve wave-2 --plan jcs1-sha256:9f2c... --actor github:alice
       ```
     </TabItem>
     <TabItem label="sealed">
       ```bash
       npx terragucci approve wave-2 --plan jcs1-sha256:9f2c... --actor github:alice --sign ~/.ssh/id_ed25519
       ```

       `--actor` must be your principal in `.chant/allowed_signers`. Left out, `--sign` uses git's `user.signingkey` when `gpg.format` is `ssh`.
     </TabItem>
   </Tabs>

   | `terragucci approve` | Does |
   |---|---|
   | with no flag | fetches `chant/lifecycle`, finds the waiting wave, prints its roots and destroys, and runs `chant approve tf-apply wave-<k> --plan <digest>` for the digest that wave planned |
   | `wave-<k>` | picks the wave when several wait |
   | `--plan <digest>` | the digest you read: approves only a wave waiting for exactly it, and otherwise approves nothing and exits 1, naming the digest waiting. Use it whenever you read the plans somewhere other than this command's own output, such as a chat message or the plan note. |
   | `--actor` | the name the approval records; pass it on your own machine, where chant would otherwise record `$USER` |
   | `--sign` | seals the approval; the default under `approval: sealed` |
   | `--dry-run` | prints the command and runs nothing |
   | `--no-resume` | records the approval and starts nothing |

   The approval binds that digest only; a wave that plans differently is refused as changed.

   <Captured step="wave-refused" cmd="just example approve" optional />

   The approval is one line appended to `_gates/tf-apply.jsonl` on `chant/lifecycle`, in a commit of its own:

   <Shot step="approved" view="record" alt="The approval commit on chant/lifecycle in Forgejo, Gate resolution record: it appends one line to _gates/tf-apply.jsonl, a human approval of wave 4 resolved by terragucci-admin, binding the plan digest of the pending line above it and sealed with an ssh signature" />

4. Let the wave run again.

   `terragucci approve` starts it again right after it records the approval, with your forge token: `GH_TOKEN` (or `gh auth login`) on GitHub, `GITLAB_TOKEN` on GitLab, `FORGEJO_TOKEN` on Forgejo. Without one it says so. With [`apply.resume`](/terragucci/reference/pipeline/#resume-after-an-approval) set, the resume job applies the wave within that many minutes of the approval, whoever recorded it. Otherwise, or after a pull request review under `approval: pr-review`, run it again by hand:

   | Situation | How to re-run |
   |---|---|
   | `apply.when: merge` (the default), GitHub or Forgejo | Comment `/terragucci apply` on the merged pull request (add `wave-2` to stop after that wave), or re-run the job. Needs write access. |
   | `apply.when: merge`, GitLab | With `comments:` set, comment `/terragucci apply` on the merged merge request; the comments job retries the first apply job that did not succeed on its next run. `wave-<n>` is refused, since GitLab runs the waves after a retried one. Needs Developer or above. Without `comments:`, retry the job. |
   | `apply.when: pull-request` | Comment `/terragucci apply` on the open pull request again. The mode and the signers come from the default branch, so the pull request cannot relax them or add its own approver. The forge's review is also required. |

   The comment approves nothing.

   | The wave or comment | Outcome |
   |---|---|
   | a wave without an approval that counts in its mode | waits, with the command in the reply |
   | a wave whose plans changed after the approval, before they applied | refused |
   | a wave planning anew after its approved plans applied | waits for an approval of the new plans |
   | an approved wave | applies, resuming where it stopped |
   | a comment that fails a check | runs nothing; the reply names the check ([the checks](/terragucci/reference/pipeline/#when-a-comment-runs-nothing)) |

   [Apply a merged pull request](/terragucci/guides/re-plan-from-a-comment/#apply-a-merged-pull-request) and [Apply before merge](/terragucci/reference/pipeline/#apply-before-merge) list what each refuses.

   In the example, after the module bump's wave 4 was refused and its new plans approved, `/terragucci apply` on the merged pull request resumed the waves and wave 4 applied:

   <Shot step="approved" view="reply" alt="terragucci's reply to /terragucci apply on the merged module bump pull request in Forgejo: it applied waves 1, 2, 3 and 4 of the pull request at its merge commit, and links the run" />

   <Shot step="approved" view="log" alt="The apply-comment job's log: wave 4 of 4 plans eight roots with 11 changes and 1 destroy, its approval mode is sealed, it is approved by terragucci-admin for this digest, each root applies, and wave 4 of 4 applied" />

   The report then shows the wave as approved, linked to its record.

</Steps>

## Roots on HCP Terraform

terragucci's gate reads neither HCP Terraform's run approvals nor its locks. Set workspaces to local execution. Remote execution adds HCP's own approvals and locks.

## Set up the signers file

Only `approval: sealed` reads it. With that key in `terragucci.yml`, `terragucci init` lists each wave under `identity.gates`, so `chant approve` asks for `--sign` too.

<Steps>

1. In a reviewed pull request to the default branch, add `.chant/allowed_signers`, one line per approver, in ssh-keygen's allowed_signers format. `terragucci init --signer github:alice` writes the first line from your `git config user.signingkey` when the file does not exist yet:

   ```text
   github:alice ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...
   github:bob ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABgQ...
   ```

   | Line | Counts? |
   |---|---|
   | `ssh-ed25519` | yes |
   | `sk-ssh-ed25519@openssh.com` | yes |
   | `ssh-rsa` | yes |
   | `namespaces="..."` | only if it lists `chant-gate` or `*` |
   | `valid-after`, `valid-before` | ignored |
   | `cert-authority` | ignored |
   | a pattern principal (`*`, `?`, `!`) | ignored |

   To move the file, set its path in `.chant/trust.json`, e.g. `{"schema": 1, "signers": "security/allowed_signers"}`. The agent comment refuses changes to it.

2. List people only. An agent's or CI job's key does not belong here.

3. Protect `chant/lifecycle` against force pushes and deletion (next section).

</Steps>

### Which commit the rule is read from

The `approval` key in `terragucci.yml`, the signers file, `.chant/trust.json` and `chant.workspace.json` are read from base, the applied commit's first parent. A pull request's change to them governs only later merges: one that switches `sealed` to `ledger` is still judged sealed.

| Merge method | Base is | Safe |
|---|---|---|
| Merge commit | the default branch before the merge | yes |
| Squash | the default branch before the merge | yes |
| Rebase of one commit | the default branch before the merge | yes |
| Rebase of several commits | the pull request's own next-to-last commit | no: merge with a merge commit or a squash |

| A change that turns sealing off for later merges | Applies when |
|---|---|
| `approval` set to `ledger` | always |
| `chant.workspace.json` deleted, or its `identity.gates` emptied | `terragucci.yml` sets no `approval` |

Give those changes the same review as the signers file. The [agent comment](/terragucci/reference/pipeline/#the-agent-comment) refuses them.

## Who can push to `chant/lifecycle`

| Who pushes | What | With |
|---|---|---|
| an approver | approval records, as fast-forwards | their own credentials |
| the apply job | pending records | its token (`github.token`, or `GITLAB_TOKEN` on GitLab); on GitHub no rule can tell it from another workflow |

| Mode | What a pushed line counts for |
|---|---|
| `sealed` | nothing, unless its seal verifies against the signers file at base |
| `ledger` and `pr-review` | every line of the digest counts, so who can push here is who can approve |

Protection keeps history from being rewritten.

| Forge | Protect `chant/lifecycle` with |
|---|---|
| GitHub | a ruleset or protection rule blocking force pushes and deletion, with pull requests and status checks off. |
| GitLab | a protected branch with push and merge allowed to a role your approvers and `GITLAB_TOKEN` both hold, force push off. |
| Forgejo | a protected branch rule with push for everyone with write access and force push off. |

## If the wave refuses instead

When any root's plan changed after you approved and before the wave applied, the wave applies nothing. Once it has applied, the next change waits for a new approval instead. [Fix a refused wave](/terragucci/guides/fix-a-refused-wave/) covers that.
