## Result

A pipeline whose roots are your [Terramate](https://terramate.io) stacks, applied in the order Terramate gives them, a layer at a time behind the same gate as plain roots.

## Already in Terramate

Terramate and Terramate Cloud already do part of this work:

| Feature | What it does |
|---|---|
| [Orchestration](https://terramate.io/docs/cli/orchestration/) | `terramate run` runs parent stacks before their children, in the [order](https://terramate.io/docs/cli/orchestration/order-of-execution) `after` and `before` set, in parallel with `--parallel` |
| [Change detection](https://terramate.io/docs/cli/change-detection) | `--changed` limits a run to the stacks git shows changed, including those whose local modules changed |
| [CI/CD workflows](https://terramate.io/docs/cli/automation/) | preview, deployment and drift check workflows for GitHub Actions, GitLab CI and Bitbucket Pipelines |
| [Deployments](https://terramate.io/docs/cloud/deployments/) (Terramate Cloud) | a searchable history of every deployment, with alerts when one fails |
| [Drift management](https://terramate.io/docs/cloud/drift/) (Terramate Cloud) | drift checks after a deployment and on a schedule, with alerts and reconciliation jobs in your CI |

If ordered runs of the changed stacks and Terramate's own workflows already fit your team, you may not need terragucci's waves.

## Added by terragucci

- Each layer waits at its own gate. An approval binds the wave's plan digest and counts only from someone with no hand in the change.
- A wave whose plans moved since the approval applies nothing.
- A stack that reads an `input` is never planned on its `mock`; it waits for its upstream's state ([Outputs sharing](#outputs-sharing)).
- `init` writes the pipeline for Forgejo as well as GitHub and GitLab.

## Prerequisites

| You need | Why |
|---|---|
| `terramate.tm.hcl` at the repo root, or a `stack.tm.hcl` below it | `init` detects Terramate from it |
| Terramate on the path, or `TERRAGUCCI_TERRAMATE` naming it | `init` runs `terramate list` and `terramate experimental run-graph` |
| Generated code committed and up to date | the jobs plan what git holds |
| A remote backend for each stack, such as `s3` | each job starts from a fresh checkout |
| terragucci installed ([Get your first plan note](/terragucci/getting-started/)) | `init` writes the pipeline |

## Steps

<Steps>

1. Run init.

   ```bash
   npx terragucci init --dry-run
   ```

   It prints the stacks and how many waves they make:

   ```text
   found Terramate (terramate.tm.hcl): 3 stacks in 2 waves from terramate list and the stacks' order, ...
   ```

2. Write the pipeline.

   ```bash
   npx terragucci init
   ```

   Commit it and open a pull request.

</Steps>

## Stacks

| What | How |
|---|---|
| A root | a stack `terramate list` names that holds Terraform, by its directory, such as `stacks/app` |
| A stack with no Terraform | not a root; the order through it is kept |
| Leaving a stack out | a `.tmskip` file in its directory, as Terramate reads it |
| `roots` and `synth` | refused: Terramate decides the stacks |

## Waves

```hcl
stack {
  id    = "app"
  after = ["tag:net"]
}
```

| What | How |
|---|---|
| Order | `after` and `before`, with stack paths, directories and `tag:` filters, as `terramate experimental run-graph` resolves them |
| Nesting | a parent stack runs before the stacks under it |
| An `input` block | puts the stack after the one it reads |
| `terraform_remote_state` between stacks | puts the reader after the stack it reads, as for plain roots |
| Each wave | one layer, in its own apply job behind its own gate |
| A path in `after` or `before` that names no stack, or a cycle | `init` stops and names it; Terramate only warns about the path |
| `waves.canary` | the canary stacks' layers go first |

## Jobs

Every job installs Terramate 0.17.3, checked against the release's `checksums.txt`, then runs `terragucci terramate generate` before it reads the stacks:

| Step | |
|---|---|
| `terramate generate --detailed-exit-code` | when it would change a file, the job fails, naming the file; run `terramate generate` and commit, as `terramate run` asks too |
| Edges | each stack's order and inputs, written to `.terragucci-terramate.json` beside it in the job |

## Pull requests

A pull request plans the stacks its diff touches, and every stack that runs after one of them.

| A pull request that changes | Plans |
|---|---|
| `stacks/network` | `stacks/network`, then `stacks/app`, whose `after = ["tag:net"]` matches it |
| a global in `terramate.tm.hcl`, with the generated code | every stack whose generated files changed, and the stacks after them |
| a global, without the generated code | nothing: the check fails on the stale code |

## Outputs sharing

An `input` block reads another stack's output:

```hcl
input "net_name" {
  backend       = "default"
  from_stack_id = "network"
  value         = outputs.name.value
}
```

The job reads the upstream's outputs from its state, once it has a cloud credential, and fills the variable Terramate generated. While the upstream has no state, the stack is held back rather than planned on its `mock`, and the plan note says which stack it waits for. The `sharing_backend` command is not run; the stack's own binary reads the state.

A pull request reads the upstream's applied state, never its plan. When one change edits both stacks, the review shows the reader planned on the upstream's old value. After the merge, the reader's wave plans on what the upstream's wave applied, which nobody reviewed. When the upstream's plan in that push changes an output the reader reads, or leaves it known only after apply, the reader's wave waits for an approval of its plan even under `gate: on-destructive` with nothing destroyed; only `gate: never` applies it without one. The wave's log names the read, the outputs and the plan that changed them. The apply finds the upstream's plan as it does for a [`terraform_remote_state` read](/terragucci/concepts/waves-and-approvals/#linked-roots), and on the commit's first run a plan that changes nothing holds nothing. With no plan of the upstream to read, as in a project with no `reports` bucket, the reader's wave waits whenever its plan changes something.

| `value` | Read |
|---|---|
| `outputs.<name>.value` | that output |
| `outputs.<name>.value.key` or `["key"]` | a key inside it |
| Anything else, such as a function call | refused; read the upstream with a `terraform_remote_state` data source |
| A `from_stack_id` no stack has | refused |

## Not read

Terramate's `watch` files, scripts, `wants` and `wanted_by`, and Terramate Cloud. terragucci's own affected selection and [steps](/terragucci/guides/run-steps/) run instead. A drift pull request, `rollouts` and `generate` are refused, since their edits would land in code `terramate generate` owns; `respond.drift: attribute` names who changed each value in the drift issue.
