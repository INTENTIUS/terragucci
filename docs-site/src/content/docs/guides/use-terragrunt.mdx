## What you end up with

A pipeline that checks with `terragrunt hcl fmt` and `hcl validate`, plans the units a pull request reaches, and applies a wave at a time behind the same gate as plain roots.

## Before you start

- A Terragrunt repo with a `root.hcl` or `terragrunt.hcl`.
- Terragrunt 1.1 or later.
- terragucci installed: [Get your first plan note](/terragucci/getting-started/) covers it.

## Steps

<Steps>

1. Run init.

   ```bash
   npx terragucci init --dry-run
   ```

   Each unit is a root, taken from `terragrunt find`, so `.terragrunt-filters` is honoured. Explicit stacks are not supported: `init` skips a directory holding a `terragrunt.stack.hcl` and names it in its notes.

   Without Terragrunt on the path, `init` reads the units' `dependency` and `dependencies` paths to cut the waves; the apply jobs check them with `terragrunt find`.

2. Name the tool Terragrunt calls. `binary` names the tool Terragrunt runs underneath:

   ```yaml
   binary: tofu
   ```

3. Tune it, if you need to. An optional `terragrunt:` block sets version, parallelism, roles by unit path, excluded units and how dependents are planned; see [terragucci.yml keys](/terragucci/reference/config/#the-terragrunt-block).

   ```yaml
   terragrunt:
     exclude: ["live/sandbox/**"]
     dependents: follow
   ```

4. Write the pipeline.

   ```bash
   npx terragucci init
   ```

   Commit the pipeline, and under `approval: sealed` [`chant.workspace.json`](/terragucci/concepts/glossary/#chantworkspacejson), and open a pull request. Under `sealed`, set up the signers file before the first wave waits, as [Approve a waiting wave](/terragucci/guides/approve-a-wave/) describes.

</Steps>

## What is different in a Terragrunt repo

| What | How |
|---|---|
| Which units a change reaches | Terragrunt's own change detection, plus files a module reads with `file()`, modules called from inside modules, and stack templates |
| Units that depend on a changed unit | a later wave than the unit they read from |
| `mock_outputs` | a unit whose plan would read mock values waits for its upstream to apply, so no approval covers a made-up value |
| Each wave | one dependency layer, canary layers first, in its own apply job. One `terragrunt run --all` saves the plans and a second applies them. The last job also runs any layer added since `init` |
| The gate | as for plain roots, one gate per wave; the set digest covers the units whose plan changes a resource or an output |
| Credentials | a plan role and an apply role chosen by the unit's path; a unit that sets its own `iam_role` keeps it |
| `/terragucci apply` | on a merged pull request (GitHub, Forgejo) reruns its waves from the merge commit behind the same gate, with [these refusals](/terragucci/guides/re-plan-from-a-comment/#apply-a-merged-pull-request); it approves nothing |
| When a change applies | after it merges, by default. With `apply.when: pull-request` (GitHub, Forgejo), `/terragucci apply` on the approved open pull request applies its waves of units from the head: [Apply a pull request before it merges](/terragucci/guides/apply-before-merge/) |
| Locks before merge | on units: a changed unit and the units whose `dependency` blocks name it; a change outside every unit's directory locks every unit ([Locks](/terragucci/guides/apply-before-merge/#locks)) |
