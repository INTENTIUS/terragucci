## Result

A value reaches a root by name, and nothing terragucci writes holds it:

| Piece | How | Section |
|---|---|---|
| Inputs | a root reads a secret by name from the forge's store (`pass.secrets`) or from a cloud's secret store (`secrets`); the config holds names and paths, never values | [Inputs](#inputs), [Steps](#steps) |
| Cloud access | with `oidc`, each job trades the forge's OIDC token for a cloud role, so no long-lived cloud key is stored | [Cloud access](#cloud-access) |
| Outputs | sensitive values are redacted in the plan files, the note, the report and terragucci's log; messages carry no plan values | [Redaction](#redaction) |
| Tokens | forge tokens are removed from the environment the binary, Terragrunt and the policy engine start with | [Tokens](#tokens) |
| State | the backend's encryption and each environment's state roles; an export needs a second person | [State](#state) |

## Inputs

<Tabs syncKey="forge">
  <TabItem label="GitHub">
    `pass.secrets` maps repository secrets by name into the jobs that plan and apply. A workflow on any branch a writer pushes can read a repository secret. An [environment secret](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#environment-secrets) reaches only the jobs of that environment, past its deployment branch rule: name an environment's roots in [`environments`](/terragucci/reference/config/#environments) and its apply jobs run in it ([Separate environments](/terragucci/guides/separate-environments/)).
  </TabItem>
  <TabItem label="GitLab">
    `pass.secrets` is not needed here. An unprotected variable reaches every branch's pipelines. A [protected variable](https://docs.gitlab.com/ci/variables/#protect-a-cicd-variable) reaches only protected refs, and one with an [environment scope](https://docs.gitlab.com/ci/variables/#environment-scope) only that environment's jobs.
  </TabItem>
  <TabItem label="Forgejo">
    `pass.secrets` maps repository secrets by name, as on GitHub. A workflow on any branch a writer pushes can read them, and Forgejo has no environment secrets: keep an environment's secrets apart with a repository of its own.
  </TabItem>
</Tabs>

## Steps

<Steps>

1. Put the value in your forge's secret store, named as the root reads it, such as `TF_VAR_db_password` (on GitLab, a masked CI/CD variable). To keep it in AWS Secrets Manager, GCP Secret Manager or Azure Key Vault instead, read it there with the root's own identity through [`secrets`](/terragucci/reference/config/#from-a-clouds-secret-store), and skip step 3.

2. Mark the variable sensitive in the root:

   ```hcl
   variable "db_password" {
     type      = string
     sensitive = true
   }
   ```

3. Name the secret in `terragucci.yml`. The pipeline holds the name, never the value:

   ```yaml
   pass:
     secrets: [TF_VAR_db_password]
   ```

   `config check` refuses a value written in place of a name. On GitLab every job reads the CI/CD variables already, so the key changes nothing there.

4. Check the file and write the pipeline again:

   ```bash
   npx terragucci config check
   npx terragucci init
   ```

   Each job that plans or applies gets the secret as an environment variable of that name; [Secrets and variables you pass](/terragucci/reference/environment/#secrets-and-variables-you-pass) lists the jobs that get none.

5. Open a pull request. When the plan held a sensitive value, the note says so:

   ```text
   Sensitive values are redacted in the stored plans (2).
   ```

</Steps>

## Redaction

The binary's `show -json` prints sensitive values in plain text. Each one is redacted before a plan is kept anywhere.

| Where | The value becomes |
|---|---|
| `plan.json` and the report | `(sensitive, redacted by terragucci)`, wherever the value appears, also in an attribute the plan does not mark |
| `plan.txt` and the plan note | `(sensitive value)`, as the binary prints it, wherever the value appears |
| a policy denial or warning | redacted before it reaches the report, the note or the log |
| a write-only attribute | its version (`*_wo_version`); the value is never in the plan |
| an ephemeral value | not reported |
| a value [`secrets`](/terragucci/reference/config/#from-a-clouds-secret-store) read from a cloud's store | redacted as a sensitive value, whether or not its variable is marked: wherever it is a whole value of the plan, and wherever a value of eight characters or more appears in the note, the report and terragucci's log lines |

Plan digests are taken before redaction, so an approval binds the plan as planned. The policy engine reads the unredacted plan.

A chat or webhook message names the wave and links the run; it carries no value from a plan. A webhook's address is a secret and is never printed.

## Cloud access

With [`oidc`](/terragucci/reference/environment/#cloud-roles-over-oidc), every job that reaches the cloud trades the forge's token for a role, a service account or a client, so no cloud key is stored in the forge. The reports bucket takes the same identity through `reports.role`, or the job's own role. Keys are the fallback only: `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, or `AZURE_STORAGE_KEY`, as secrets the jobs that plan get ([Reports](/terragucci/reference/environment/#reports)). Leave them unset and set `reports.role`, or give the job's role write access to the reports, to store none.

## Tokens

| Token | Held by | Kept from |
|---|---|---|
| the run's own token, or `GITLAB_TOKEN` | the generated jobs that post or push | the binary, Terragrunt and the policy engine, in every stage that runs them ([Forge tokens](/terragucci/reference/environment/#forge-tokens)) |
| any forge token, on GitHub and Forgejo | the steps of the `check`, `plan` and `replan` jobs before the step that runs the pull request's code; on GitHub, the later steps hold only the artifact upload's runtime token, and on Forgejo the step that runs the code is the job's last, its report going on to a job in a fresh container | the steps that run that code, and on Forgejo with `oidc` the token-request variables, which carry the run's token; [Token scrub limits](/terragucci/reference/threat-model/#token-scrub-limits) has each row |
| the merge token, the agent's token, the relay's token and the signing keys | the jobs, relay and people [Access and identity](/terragucci/standards/access-and-identity/#secrets-and-who-holds-them) lists | every other job |

## Limits

| Case | What happens |
|---|---|
| a value not marked sensitive | it is in the plan, the note and the bucket like any other attribute; mark it, or keep the bucket private |
| a provider or a step that prints a value | it reaches the job log as printed; a value from `secrets` is masked there on GitHub and Forgejo, and on GitLab replaced only in what terragucci prints |
| a passed secret in the plan job | the pull request's code runs there with it, as with the providers' credentials; a fork's pull request gets no plan job |
| the state | holds every secret its resources hold; reports and the bucket keep version ids only, and [`terragucci state export`](/terragucci/guides/export-a-state-version/) writes a version only to the machine of the person who runs it |

## State

A state holds every secret its resources hold. It stays in your backend, under the backend's encryption. Each plan report counts the sensitive values a root's state holds. When a write-only argument or an ephemeral resource could keep one out of state on the root's binary and provider versions, the tip [`terragucci-secret-in-state`](/terragucci/reference/tips/#terragucci-secret-in-state) names it, and the [estate page](/terragucci/guides/see-every-project/#secrets-in-state) lists the counts per root. Under [choudoufu](/terragucci/concepts/glossary/#choudoufu), an estate keeps its records in a record store, and the tip [`terragucci-choudoufu-secrets`](/terragucci/reference/tips/#terragucci-choudoufu-secrets) names each root whose `live` block lets secret values reach it. Jobs reach it with each environment's state roles ([Keep each environment's roles to its own state](/terragucci/guides/scope-state-access/)). Reports and the bucket keep version ids only. [`terragucci state export`](/terragucci/guides/export-a-state-version/) writes a version to the machine of the person who asked, once someone else approved the request.
