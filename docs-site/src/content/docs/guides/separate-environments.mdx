This page is optional reading for a repo that applies more than one environment, such as dev and prod. terragucci runs without any of it.

## Result

A job from a branch, or from another environment, cannot run on prod's apply runner, read prod's secrets or assume prod's apply role. Most of that is set on the forge and in the cloud. terragucci writes each environment's apply jobs to match those settings, and checks for mistakes.

A check inside a job catches mistakes, such as a hand-edited workflow or a mistyped runner label. Someone who can edit the workflow can delete the check too, so it is the forge's settings and the cloud's trust that enforce the separation.

## Prerequisites

| You need | Why |
|---|---|
| Each environment's roots named in [`environments`](/terragucci/reference/config/#environments), with its own apply role or identity and, where it has one, its own `runner` | each environment then applies in [jobs of its own](/terragucci/concepts/waves-and-approvals/#one-apply-job-per-identity), which the settings below can tell apart |
| [`oidc`](/terragucci/reference/environment/#cloud-roles-over-oidc) set up | the cloud's trust can only check a token's claims |

[`config identities`](/terragucci/reference/cli/#config-identities) prints, for each environment, the subject, audience, forge environment and runner of its plan, deciding, apply and drift jobs. The Terraform provider's [`terragucci_environments` and `terragucci_trust_policy`](/terragucci/guides/manage-the-control-repo-with-terraform/#read-the-environments-trust) give the same values to the resources that make your roles, environments and runner groups.

## Runner hosts

A runner that holds credentials of its own gives them to every job it takes, with no token and no trust condition in the way. Keep these off the hosts that run apply jobs, and off every other runner:

| Credential | Where it comes from | Keep it off by |
|---|---|---|
| An instance's role | an AWS instance profile, a GCP VM's service account, an Azure managed identity | giving the runner's machine no role, or one that reaches nothing terragucci manages |
| The metadata endpoint | `169.254.169.254` and `metadata.google.internal`, which hand out the instance's credentials | blocking it from the job containers; on AWS, requiring IMDSv2 with a hop limit of 1 keeps a container on a bridge network from reaching it |
| Mounted keys | a volume the runner mounts into each job, or a key file on a host that runs jobs without a container | mounting nothing the jobs do not need; Forgejo's [`container.valid_volumes`](https://forgejo.org/docs/latest/admin/actions/security/#runner-configuration) left empty |
| Cloud config files | `~/.aws`, `~/.config/gcloud`, `~/.azure` in the runner user's home | a runner user with no cloud login |

A runner that keeps files or processes between jobs can also carry one job's state into the next. The tip [`terragucci-persistent-runner`](/terragucci/reference/tips/#terragucci-persistent-runner) names apply runners that the plan jobs, or another environment's apply jobs, could also take. Give them labels of their own, and use runners that start clean for each job, such as Forgejo's [ephemeral runners](https://forgejo.org/docs/latest/admin/actions/security/#ephemeral-runners).

## Forgejo: one ref, one subject

A Forgejo token's subject names the repository and the ref, nothing else. Two environments that apply from the same branch carry the same subject, so no cloud trust can tell their jobs apart: prod's apply role trusts dev's apply job as well. The runner and the secrets cannot be held to one environment either, as the table shows. Two ways out:

| Way | How | What it separates |
|---|---|---|
| A repository per environment | each environment's roots in a repository of its own, with its own `terragucci.yml`, a runner registered to that repository and its own secrets; each apply role trusts its own repository's subject | runner, secrets and role |
| A protected branch per environment | [`apply.branches`](/terragucci/reference/config/#apply-from-other-branches) maps a branch such as `release` to prod's roots; protect `release`, and have prod's apply role trust `ref:refs/heads/release` alone | the role; the runner and the repository's secrets stay open to every branch's workflow |
