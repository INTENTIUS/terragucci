## The lifecycle around your roots

terragucci carries a root through review, rollout and the watch that follows, and you write none of the pipeline. The stages are built on [chant](/terragucci/concepts/glossary/#chant), which renders each one into a workflow for your forge. [How terragucci works](/terragucci/concepts/how-it-works/) follows one change through all of them. Your Terraform code and its state stay yours.

<Lifecycle />

## One note for two hundred plans

A change to a shared module can touch hundreds of roots. Your reviewer gets one note on the pull request that groups the roots taking the same change. Every destroy and every replacement is still named.

<PlanNote />

The note links to the full report. It opens on the destroys and the outliers with the identical groups folded away, and every root in it links to its full plan. Scripts read the same data as JSON. [The plan report](/terragucci/reference/report/) shows both.

## Rollouts in waves

The change goes out a few roots at a time, the [canary](/terragucci/concepts/glossary/#canary) roots first. By default a wave that destroys or replaces something waits for an approval, and that approval covers exactly the plans it was given.

<Waves />

The report lists each wave with its [set digest](/terragucci/concepts/glossary/#set-digest) and links the approval record that let it go out.

A pinned module rolls out the same way: one pull request per wave, across as many repos as use it.
