## Pull request automation

These are plain CI jobs in your pipeline. None of them runs a coding agent.

| On a pull request | How you start it | Forges | Page |
|---|---|---|---|
| One grouped plan note and a `terragucci/plan` status | open or push to the pull request | all three | [Get your first plan note](/terragucci/getting-started/) |
| Tips and policy results on the plan | on by default with the plan; `tips: false` turns tips off, `policy` adds checks | all three | [Tips](/terragucci/reference/tips/), [Policy](/terragucci/reference/policy/) |
| A re-plan | comment `/terragucci plan [root]` | all three; GitLab through the comments schedule | [Re-plan from a comment](/terragucci/guides/re-plan-from-a-comment/) |
| Root locks | comment `/terragucci lock` or `/terragucci unlock`; `locks: plan` locks from the first plan | GitHub and Forgejo | [Locks](/terragucci/guides/apply-before-merge/#locks) |
| Apply before merge, then merge after the last wave | `apply.when: pull-request`, then comment `/terragucci apply [wave-<n>]` | GitHub and Forgejo | [Apply before merge](/terragucci/guides/apply-before-merge/) |
| An approval for a waiting wave | `approval: ledger`, `pr-review` or `sealed`; run `terragucci approve` | all three | [Approve a waiting wave](/terragucci/guides/approve-a-wave/) |
| A recorded policy override | a listed person runs `terragucci override` | all three | [Override a policy denial](/terragucci/guides/approvals-runbook/#override-a-policy-denial) |
| Comment commands on GitLab | `comments:` sets the schedule that answers merge request notes | GitLab | [Re-plan from a comment](/terragucci/guides/re-plan-from-a-comment/) |

### Opt-in: coding agent

Two features run a coding agent. Both are off until you set them up, and both need a model API key in your forge's secrets. Nothing else in terragucci runs an agent.

| Feature | Turn it on | Forges | Page |
|---|---|---|---|
| Comment `/terragucci agent <ask>` and an agent commits the change to the pull request | `agent.comment` in `terragucci.yml` | GitHub and Forgejo | [Have an agent change a pull request](/terragucci/guides/agent-change-a-pull-request/) |
| A summary of what moved in a refused wave | add the explain-refusal job to the pipeline by hand | all three | [Have an agent summarize a refused wave](/terragucci/guides/agent-refused-wave/) |

## One note for two hundred plans

One pull request note groups roots taking the same change and names every destroy and replacement.

<PlanNote />

[The full report](/terragucci/reference/report/) opens on destroys and outliers, links every root's plan, and comes as JSON too.

## Rollouts in waves

The change goes out a few roots at a time, the [canary](/terragucci/concepts/glossary/#canary) roots first. By default a wave that destroys or replaces something waits for an approval, and that approval covers exactly the plans it was given.

<Waves />

The report lists each wave with its [set digest](/terragucci/concepts/glossary/#set-digest) and links the approval record that let it go out.

A pinned module rolls out the same way: one pull request per wave, across as many repos as use it.

## More with choudoufu

Set `binary: choudoufu` in `terragucci.yml` and the stages gain these. [The glossary](/terragucci/concepts/glossary/#choudoufu) says what choudoufu is.

| You get | Where you see it |
|---|---|
| A live check on every pull request, before any plan, with no cloud credentials | [the `tf-check` log and check report](/terragucci/reference/stages/#check) |
| No state file to host or lose: each resource carries a tag the next plan reads back | [your cloud's own tags](/terragucci/guides/use-a-binary/#choudoufu) |
| How long a wave waited for a state lock, and how many tries it took, on a backend that locks | [the report, the trace and a metric](/terragucci/reference/observability/#state-lock-waits) |
| Which provider calls were slow, and the resource each was for | [the report's provider calls](/terragucci/reference/observability/#what-the-report-lists) |
| Reports that stay readable past a span budget on a large estate, with timings summed by resource type | [the report's summed timings](/terragucci/reference/observability/#what-the-report-lists) |

## Hand the setup to your agent

You can skip this. [Add terragucci to a repo](/terragucci/guides/add-to-a-repo/) gives the same steps by hand, and only the [opt-in agent features](#opt-in-coding-agent) run an agent.

Paste this into Claude Code, Codex or Cursor in your Terraform, OpenTofu or Terragrunt repository. [The agent page](/terragucci/getting-started/agents/) says what the agent does. It never applies and never approves.
