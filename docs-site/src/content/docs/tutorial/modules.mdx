:::note[Where the example stands]
Booted with `just example up`. `just example reset` gets you back to that from any step, and removes the release tags this page makes.
:::

When roots pin a published version, a module change reaches no root until a pin moves. `tf-publish` publishes a module version, and `tf-rollout` moves the pins with one pull request per wave.

<Steps>

1. Run the scenario:

   ```bash
   just example change pin
   ```

   It tags `modules/service` at `1.0.0` with `tf-publish` and pins the twelve service roots to that tag on main. It publishes the changed module as `1.1.0`, then runs `terragucci rollout modules/service --mode apply`. Here `apply` means opening the pull request; no `terraform apply` runs until it merges.

   <Captured step="pin" />

2. Read the canary wave's pull request, for the four dev services. The rollout took the newest version and moved each of their pins:

   <Shot step="pin" view="pull" alt="The rollout's wave 1 pull request on the local Forgejo, opened for the four dev service roots" />

   <Shot step="pin" view="files" alt="The pull request's files: each dev service main.tf moves its ref from modules/service/v1.0.0 to v1.1.0" />

   | Version | Git tag, the roots' `ref` | Roots pinned to it |
   |---|---|---|
   | `1.0.0` | `modules/service/v1.0.0` | every service root whose wave has not merged |
   | `1.1.0` | `modules/service/v1.1.0` | the dev services, once this pull request merges |

3. Merge it, and let the apply on the merge commit finish.

4. Open the next wave:

   ```bash
   just example rollout
   ```

   It runs the same `terragucci rollout` command. Each run takes at most one step, so the next wave opens only once the last has applied.

</Steps>

[Publish your modules](/terragucci/guides/publish-modules/) adds the publish job, and [Roll out a new module version](/terragucci/guides/roll-out-a-module-version/) has every step.
