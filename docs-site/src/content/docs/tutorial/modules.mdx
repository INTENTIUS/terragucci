:::note[Where the example stands]
Booted with `just example up`. `just example reset` gets you back to that from any step, and removes the release tags this page makes.
:::

When roots call a module from the repo, a change reaches every root that calls it, as `just example change module-bump` showed with twelve plans. When roots pin a published version, a change to the module reaches no root until a pin moves. `tf-publish` publishes a module at a new version, and `tf-rollout` moves the pins for one wave at a time, each wave its own small pull request.

The example's roots call `modules/service` by path, so the scenario first does what a team does when it starts versioning a module. `tf-publish` tags `modules/service` at `1.0.0` in git. The twelve service roots are then pinned to that tag in one commit on main, together with a new output on the module, and the pipeline applies it. The changed module is published as `1.1.0`, and the rollout runs:

```bash
just example change pin
```

The last command it ran is `terragucci rollout modules/service --mode apply`. Here `apply` means opening the pull request; no `terraform apply` runs until it merges. With no version given, the rollout takes the newest one published, `1.1.0`, and opens the pull request for the first wave. That wave is the canary, the dev services. It changes only their `main.tf` files, and the `ref` in each moves from `modules/service/v1.0.0` to `modules/service/v1.1.0`. The usual stages plan it as they plan any pull request.

Merge it, and let the apply on the merge commit finish. Then run the rollout again from a clone of the example repo with `terragucci rollout modules/service --mode apply`. Each run takes at most one step, so the next wave opens only once the last one has applied. [Publish your modules](/terragucci/guides/publish-modules/) adds the job that publishes on every merge, and [Roll out a new module version](/terragucci/guides/roll-out-a-module-version/) has every step.
