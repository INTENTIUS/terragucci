Every version a job runs is pinned in the repo and moved by a reviewed pull request, terragucci's own included.

| What | The pin lives in | Moved by | Checked before it runs | Tip for a missing pin |
|---|---|---|---|---|
| terragucci | `@intentius/terragucci` in `package.json`, and the image tag in the pipeline, which carries the package version | `init` at the new version, in a pull request ([Upgrade terragucci](/terragucci/guides/upgrade-terragucci/)) | the image is pulled by its digest | |
| the job image | the pipeline: `ghcr.io/intentius/terragucci-<binary>:<tag>@<digest>` for the Debian set, `ghcr.io/intentius/terragucci-<binary>:<tag>-chainguard@<digest>` for the Chainguard set that `image.base: chainguard` picks, or the image [`image`](/terragucci/reference/config/#keys) names | `init` | its digest; the pipeline's header says when it is pinned by digest | |
| OpenTofu or Terraform, per root | the first of: `version` as a map of root globs, the root's `.opentofu-version` or `.terraform-version`, an exact `required_version` | a pull request by hand | a release the image does not carry is installed against the release's SHA256SUMS | `TF003`, no `required_version` |
| [choudoufu](/terragucci/concepts/glossary/#choudoufu) | `version`, one release for every root; a map is refused | a pull request by hand | SHA256SUMS | |
| Terragrunt | `terragrunt.version`, or an exact `terragrunt_version_constraint` in a unit's own `terragrunt.hcl` | a pull request by hand | SHA256SUMS | |
| Atmos | `atmos.version`, else the release this terragucci pins | a pull request by hand, or a terragucci upgrade | SHA256SUMS | |
| Terramate | the release this terragucci pins | a terragucci upgrade | its release's checksums | |
| the policy engine | the conftest and OPA releases this terragucci pins | a terragucci upgrade | a SHA-256 written into terragucci; an engine already on the path is used as it is | |
| providers | each root's `.terraform.lock.hcl` | `terragucci rollout --provider`, a wave at a time | the binary's `init` checks each provider package against the lock file's hashes | `TF002`, a provider with no version; `TF040`, no lock file; `terragucci-floating-range` |
| registry modules | the call's `version` | `terragucci rollout` | the binary's `init` | `TF004`, no `version`; `TF039`, a range |
| git and `oci://` modules | `?ref=` or `?tag=`, or the `oci://` tag | `terragucci rollout` | the binary's `init`, and with [`modules.require: attested`](/terragucci/guides/publish-modules/#require-attested-releases), the release's signature | `TF005`, no fixed `?ref=`; `TF038`, no tag or `latest` |
| a Terragrunt unit's module | its `terraform.source` | a pull request by hand | the same as the module kind | `TF043` |
| your own modules | a git tag `<module>/v<version>`, an `oci://` tag, or the registry's version list | `terragucci publish`, by the [version bump rules](/terragucci/reference/stages/#version-bump-rules) (`modules/publish`, `modules/version-bump`) | with `modules.attest`, a signed release in the release ledger | `terragucci-shared-module`, a local module ten or more roots include |

[Tips](/terragucci/reference/tips/) has each rule, and [Supply chain](/terragucci/standards/supply-chain/) what proves where each piece comes from.

Each applied wave records the binary, provider and module versions its roots ran in the project's `versions.json`. The estate page lists them per module, provider and binary with the roots on each version ([Versions](/terragucci/guides/see-every-project/#versions)), and `terragucci query` reads them as its `versions` table.

## The two image sets

Each release builds and publishes terragucci's four images, one per toolchain, in two sets, and records the digest of all eight in the package. `image.base` in `terragucci.yml` picks the set, and `init` names that set's image by its digest. Both sets carry the same engines at the same versions, chant's wave runtime and the terragucci bundle.

| | Debian (default) | Chainguard |
|---|---|---|
| Tag | `<version>-<binary><engine version>` | the same, ending in `-chainguard` |
| Base | `node:22-bookworm-slim`, by digest | `cgr.dev/chainguard/node:latest-dev`, by digest, with `cgr.dev/chainguard/wolfi-base` for the download stage |
| Node | 22 | the Node Wolfi packages: 26 when the set was built, so it moves to a newer major without a change here |
| Packages | apt | apk |
| Runs as | root | user 65532 |
| Base digest | `CI_BASE_IMAGES` in [chant](/terragucci/concepts/glossary/#chant), moved with terragucci's chant pin | `IMAGE_PINS` in chant, moved with the same pin |

A pipeline's jobs run in the image by digest, so a job gets the Node major of the set it names and a later release can change the Chainguard one. The Chainguard set's apk packages are installed at versions chant pins, so they move when chant's pins move. Each image's labels record its base: `org.opencontainers.image.base.name`, `org.opencontainers.image.base.digest` and `io.intentius.chant.image.base`, which is `debian` or `chainguard`. A terragucci release that published only the Debian images has no digest for the other set, and `init` refuses `image.base: chainguard` with that release.

## Ranges

A version range is refused for a rollout and allowed through a registry, for two different reasons:

| Where | A range such as `~> 1.0` | Why |
|---|---|---|
| `terragucci rollout` | refused, with the tip `rollout-floating-pin` | a rollout moves one pin per wave, and a range has no one version to move; a range also takes a new version without a reviewed change |
| a module from your [registry](/terragucci/guides/publish-modules/#serve-a-module-registry) | resolved by the binary to the newest release in range (`modules/registry`) | the registry protocol serves a version list; pin one version where a reviewed change should move it |

Under `modules.require: attested`, a pin that names no one release is refused, a range among them.
