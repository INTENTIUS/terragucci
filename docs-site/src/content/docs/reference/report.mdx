Each `tf-plan`, `tf-apply` wave and `tf-drift` run writes one report. The report is a JSON document, and everything a person reads is rendered from it.

## Running it

The plan job writes the report for every pull request and merge request. Its note is the one plan note, and the `terragucci/plan` status takes its counts from it. GitHub and Forgejo keep the report as the `terragucci-report` artifact, and the note links the run. GitLab keeps it with the job's artifacts and links the HTML report. Its merge-request widget reads `gitlab-terraform.json`. When [the bucket is served](#where-reports-are-kept), the note links the copy there.

To run the stage yourself, from the repo:

```bash
npx terragucci stage tf-plan
```

With no base it plans every root. On a pull request, or with `--base <ref>` or `TG_BASE`, it plans only what the change reaches. That is a root whose directory, local modules or var files changed, and every root that reads its state. A change that reaches none plans nothing, and the note says so. The files go to `terragucci-report/`:

| File | What it is |
|---|---|
| `report.json` | the report |
| `report.html` | the HTML report |
| `note.md` | the plan note |
| `summary.txt` | the grouped summary, as the job log shows it |
| `gitlab-terraform.json` | the counts for GitLab's merge-request widget |
| `roots/<root>/plan.txt` | the root's full plan, as the binary printed it |
| `roots/<root>/plan.json` | the same plan as `show -json`, with sensitive values redacted |

`--out <dir>` writes elsewhere and `--root <glob>` limits the roots; [CLI commands](/terragucci/reference/cli/#plan-and-stage) lists the rest. Terragrunt units are planned with one `terragrunt run --all` per wave. The stage exits 1 when a root refuses to plan, and still writes the report.

A `tf-drift` run writes the same files plus `issue.md`, the body of the drift issue. It has no waves and lists a deleted object as "deleted outside Terraform". See [Drift](/terragucci/reference/stages/#drift).

## What a reviewer sees

| View | Where | What it shows |
|---|---|---|
| Plan note | the pull request or merge request | groups, every destroy by name, the wave plan, the approval command, and a link to the full report |
| HTML report | wherever the report is kept | every group, root and wave, with filters, and where the run spent its time |
| Merge-request widget | GitLab | create, update and delete counts, from a `reports:terraform` artifact |
| Text summary | the job log | the grouped summary |

The plan note stays under your forge's comment limit however many roots change. The detail lives in the HTML report.

## Built for hundreds of plans

If every change plans hundreds of roots, the report is where you read them. It opens on what a reviewer looks for and folds away the rest.

<Shot step="report" view="top" alt="The top of an HTML report for a change to a shared module: twelve roots, the roots to read first, and eleven identical plans folded into one group" optional />

Open and highlighted:

- every destroy, replacement and refusal, with the attributes that forced each replacement;
- the roots whose change differs from every group;
- changes to types where one wrong value reaches far, each marked with why;
- anything declared with `prevent_destroy`;
- inside a group, the attributes that differ between roots.

The types that are highlighted, and the reason the report gives:

| Types | Why |
|---|---|
| IAM: `aws_iam_*`, `google_*_iam_*`, `azurerm_role_assignment`, Kubernetes roles and bindings | changes who may do what |
| `aws_security_group`, its rules, `google_compute_firewall`, `azurerm_network_security_*` | changes what traffic gets in or out |
| `aws_network_acl` and its rules | changes what traffic a subnet allows |
| `aws_kms_*`, `google_kms_*`, `azurerm_key_vault_key` | data encrypted under the key depends on it |
| `aws_route53_*`, `google_dns_*`, `azurerm_dns_*`, Cloudflare records | changes where names resolve |

A change to one of these that only touches tags stays folded.

Folded, one click away:

- each group of identical changes, as one diff with a count;
- updates that only touch tags or descriptions;
- values known only after apply;
- roots with no changes.

## Back to the full plan

Every root's full plan is kept beside the report, as printed and as JSON. The HTML links each group, root and named change to its plan and CI job. The note links a group to the report and a destroy to its root.

The header links the commit and the job, and the pull request if there is one. With `telemetry.trace_url` set, a run's trace id links to the trace. See [Traces and metrics](/terragucci/reference/observability/#from-a-trace-to-its-report).

The page opens on two lists that are never folded: destroys, replacements and refusals, then outlier roots.

The HTML report is one file that makes no network calls. Destroys stay pinned above its filters.

## What a script reads

`report.json` sits beside every `report.html`. The HTML also carries it inline, so a script handed only the HTML still has the data:

```bash
sed -n '/id="terragucci-report"/,/<\/script>/p' report.html | sed '1d;$d' | jq '.named[] | select(.action == "delete") | .address'
```

[Report JSON schema](/terragucci/reference/report-schema/) lists every field.

Approvals stay on your repo's [`chant/lifecycle`](/terragucci/concepts/glossary/#chantlifecycle) branch. The report links to each record and never copies it.

## Sensitive values

`show -json` prints sensitive values in plain text. Before a plan is kept, each sensitive value and the default of each sensitive variable becomes `(sensitive, redacted by terragucci)`. The report page counts them. A [policy](/terragucci/reference/policy/) reads the unredacted plan, and its denials and warnings are redacted before they reach the report, note or log. Digests are taken before redaction, so an approval binds the plan as planned.

A write-only attribute's version (`*_wo_version`) is labelled as such, since the value is never in the plan. Ephemeral values are not reported. Imports and forgets are named separately, not counted as destroys; a forget leaves the resource running.

## Where reports are kept

By default a report is a CI artifact of the plan job, kept as long as your forge keeps artifacts.

To keep them longer, name a bucket in `terragucci.yml` and run `npx terragucci init` again. The plan job then copies each report there. Any S3-compatible store works. The job assumes `reports.role` with its OIDC token when set. Otherwise it uses `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (and `AWS_SESSION_TOKEN`). With no keys it assumes `AWS_ROLE_ARN` with `AWS_WEB_IDENTITY_TOKEN_FILE`. [Keep reports in S3](/terragucci/guides/keep-reports-in-s3/#3-give-the-job-an-identity-that-writes-only-reports) says why reports get their own identity. `endpoint` sets a non-AWS store; otherwise `AWS_ENDPOINT_URL_S3` or `AWS_ENDPOINT_URL` applies. Requests are signed for `AWS_REGION` or `AWS_DEFAULT_REGION`, else `us-east-1`.

```yaml
reports:
  bucket: s3://acme-terragucci
  prefix: reports
  url: https://reports.acme.example
  role: arn:aws:iam::123456789012:role/terragucci-reports
```

`url` is the address that serves the bucket to a browser. terragucci never derives it from the bucket name. With it the note links the bucket's `report.html` and `report.json` records it as `run.report_url`; without it the note links the CI run.

A run's report and plans land under one path holding the full commit SHA: `GITHUB_SHA` (for a GitHub pull request, the test merge commit) or `CI_COMMIT_SHA` on GitLab. Links are relative, so they work in the bucket:

```
reports/github.com/acme/infra/2026/10/4f1a9c0d2e7b8a6c5d4e3f2a1b0c9d8e7f6a5b4c/tf-plan/report.html
reports/github.com/acme/infra/2026/10/4f1a9c0d2e7b8a6c5d4e3f2a1b0c9d8e7f6a5b4c/tf-apply-wave-2/report.json
```

## Tips

With `tips` on, the default, the report ends with advice on how your roots are set up. Examples are a floating version or a missing lock file. Each tip names its rule, and none fails a run or changes a gate. `tips: false` removes them. See [Tips](/terragucci/reference/tips/).

## The report index

Every upload rewrites `index.html` and `index.json` for the project and, at the top of the prefix, for all projects. Each run has a row with its counts, destroys and links. Concurrent runs each keep their row. Served as a static site, the index publishes every report in the bucket: put the site behind your identity provider and keep the bucket private. [Keep reports in S3](/terragucci/guides/keep-reports-in-s3/#5-serve-the-index) has the choices. Retention is your bucket's lifecycle rule.
