Release `0.4.28` is on npm as `@intentius/terragucci@0.4.28`, and its [GitHub release](https://github.com/INTENTIUS/terragucci/releases/tag/v0.4.28) lists every change.

| To upgrade | Run |
|---|---|
| Each repo | `npx @intentius/terragucci@0.4.28 init`, then merge the pipeline it writes |
| Each approver | `terragucci approve` where you ran [`chant approve`](/terragucci/concepts/glossary/#chant); installing terragucci is enough ([approve](/terragucci/reference/cli/#approve)) |

## In 0.4.28

- The demo's chant pipeline keeps its reports with upload-artifact@v3 on Forgejo (#1094).
- The demo runs estate each cycle so the kiosk shows DORA numbers (#1097).
- Deploy frequency divides by the span the history covers (#1099).

## In 0.4.27

- Pipeline metrics time each apply wave and each root's init, to the millisecond (#1093).

## In 0.4.26

- The stack collects pipeline metrics in Prometheus for each run and wave (#1087).

## In 0.4.25

- The demo's chant scenario runs its jobs in an image with OpenTofu and chant, so nothing downloads at job time (#1086).

## In 0.4.24

- The demo's migration step runs in a shallow checkout; a failed `up` keeps the last base (#1083).

## In 0.4.23

- The demo's failure scenario runs a real SQL Yodeler migration on Postgres, which fails on duplicate rows until the driver removes them (#1080).

## In 0.4.22

- The demo's failure scenario calls its failing step a setup step, which is what it is (#1076).
- The demo has a chant scenario: chant's own pull request loop on its own repo, run by name (#1077).

## In 0.4.21

- With `DEMO_VIEWS` set, the demo checks out each step's commit for the viewer before it writes the step, so a viewer reading demo.json finds the checkout already there (#1073).

## In 0.4.20

- Every line the demo shows says what happens, in fewer words: the intro, the scenario titles, the cards and the step lines (#1070).

## In 0.4.19

- The demo's default loop runs the Terragrunt scenario too, after the two scenarios it already ran (#1067).

## In 0.4.18

- The demo's `up` no longer dies of SIGPIPE right after bootstrap. A failure in `up` prints where it happened: its file and line, and the functions that called it (#1064).

## In 0.4.17

- The demo driver runs each scenario on its own tool's demo repo, and publishes each tool's latest clean cycle for replay (#1056).
- The demo has a Terragrunt scenario, run by name: a new unit is planned on its upstream's real planned outputs (#1057).
- Each tool's docs page says what the tool already does natively and when to use it, then what terragucci adds (#1060).
- Every string in the demo's header fits a length budget, held by lint-docs (#1061).

## In 0.4.16

- The demo driver plays an author and a reviewer, so its approvals pass the involvement rule (#1052).

## In 0.4.15

- By default the demo loop runs two scenarios, told in plain words for people new to Terraform (#1050).

## In 0.4.14

- The demo driver runs the reset during the last step's hold and polls every second, and each reset deletes the demo repo's old finished Forgejo runs beyond the newest 100 (#1047).

## In 0.4.13

- An approval counts only from someone who had no hand in the change: the pull request's author, its commits' authors and committers, the people who asked an agent for the change, and the agent's account, which `agent.login` names; `approval.require_signed: true` refuses unsigned ledger approvals (#1044).
- `terragucci init` writes `terragucci.components.json`, which lists each root as a chant component, grouped by wave under the job that applies it (#1043).
- Each demo scenario's card text is in its `about.json`, the demo driver writes it into `demo.json`, and `just lint-docs` lints it (#1041).

## In 0.4.12

- A lock file with no provider entries covers a root that uses only the built-in `terraform` provider, and every root in `example-demo/` sets `required_version` and commits its lock file (#1037).
- The demo driver copies the demo repo's pipeline runs, with their jobs, steps and log tails, into the reports bucket, and keeps the newest 30 (#1038).

## In 0.4.11

- A wave that applies records the spend of its approval whichever gate let it through, so the next push's waves wait instead of being refused as changed after approval, and on `/terragucci apply` a read unknown at review is judged by the plan that changed the upstream (#1030).
- With `waves.compose`, a wave the composed run emptied keeps its number in chant's spec, and the merge's apply composes the set the pull request reviewed (#1031).
- On a commit's first run, a plan of the upstream that changes nothing counts its outputs as known, so a push whose reader changes and whose upstream does not applies without waiting (#1033).
- `stack/demo.sh` passes the scenario label to jq as `$text`, so it runs under jq 1.6 (#1026).
- `stack/demo.sh` finds a Forgejo run by `commit_sha` when the runs API leaves `head_sha` empty (#1027).
- `stack/demo.sh` scenario 2 says each wave that read an output unknown at review waits for the driver's approval (#1029).
- `stack/demo.sh up` builds the CI images again when the checkout's commit moves (#1032).
- `stack/demo.sh up` writes the last base snapshot back before it pushes the base (#1034).

## In 0.4.8

0.4.8 fixes a security issue: in 0.4.7 and earlier, the code of a pull request re-planned with `/terragucci plan` could get a token the apply role trusts, or leave files in the Terragrunt cache that the apply jobs restore. Upgrade every repo that has a re-plan job.

| What | Where |
|---|---|
| A re-plan trades its OIDC token for the plan identities before the pull request's code runs, so that code holds no token the apply role trusts. With `oidc.azure` it plans as before and warns in its log | [Re-plan](/terragucci/reference/threat-model/#re-plan) |
| A re-plan restores the Terragrunt cache and saves none, so what a pull request's code leaves in `.terragrunt-cache` never reaches an apply job | [Re-plan](/terragucci/reference/threat-model/#re-plan) |
| `sources` refuses module and provider sources outside an allow list before `init`, and checks what `init` fetched and locked before the plan | [Allow only listed sources](/terragucci/guides/write-a-policy/#allow-only-listed-sources) |
| A change outside every root plans the roots it reaches: var files, symlinks, `terragucci.yml` settings and the synth command | [Changes outside every root](/terragucci/reference/report/#changes-outside-every-root) |
| State reads resolve when the address comes from a `-backend-config` file or a Terragrunt `remote_state` block | [Addresses outside the backend block](/terragucci/guides/track-cross-state-edges/#addresses-outside-the-backend-block) |
| Parallel Terraform plans on roots with no lock file share one provider cache with one download | [Pipeline](/terragucci/reference/pipeline/) |

- Changed for webhook receivers: the event `notify.webhook` gets is chant's [`chant.notify/v1`](/terragucci/reference/notify-event/), with the stage's outcome in `detail`, and its signature covers `<timestamp>.<body>`, where `X-Terragucci-Timestamp` carries the timestamp. A receiver that checks the old signature over the body alone refuses every event until it is updated ([Headers](/terragucci/reference/notify-event/#headers)).

## From 0.4.5

0.4.6 carries every change of 0.4.5, listed by area below. Upgrading from 0.4.4 or earlier, also note:

|---|---|
| A Terragrunt repo that uses `generate` | `terragucci generate` again, so each unit's state key reads the ephemeral suffix ([In a Terragrunt repo](/terragucci/guides/generate-root-files/#in-a-terragrunt-repo)) |

- Changed default: a pull request that changes a Terragrunt unit also previews the units that depend on it, provisional and outside every digest. Set `terragrunt.dependents: follow` to keep the old behavior ([The terragrunt block](/terragucci/reference/config/#the-terragrunt-block)).
