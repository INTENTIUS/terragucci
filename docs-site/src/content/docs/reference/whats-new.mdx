Release `0.4.66` is on npm as `@intentius/terragucci@0.4.66`, and its [GitHub release](https://github.com/INTENTIUS/terragucci/releases/tag/v0.4.66) lists every change.

| To upgrade | Run |
|---|---|
| Each repo | `npx @intentius/terragucci@0.4.66 init`, then merge the pipeline it writes, with `chant.config.ts` in a repo of plain roots |
| Each approver | `terragucci approve` where you ran [`chant approve`](/terragucci/concepts/glossary/#chant); installing terragucci is enough ([approve](/terragucci/reference/cli/#approve)) |

## In 0.4.66

The package and the images now run chant `0.124.116`. The package's GitHub and Forgejo lexicons move to `0.124.104`.

In a repo with environments the apply runs one job per environment group. `terragucci waves-spec` now names each wave's groups and the runs that each group holds. The spec used to name no groups. Every group's job then applied nothing and the merge's apply failed with the wave counted as decided, so a merge that changed dev did not apply dev.

With `promotion` set, `init` now writes `.chant/pipeline.ts` beside `terragucci.component.ts`. Each environment whose gate is not `never` waits for one approval at its stage's gate in that pipeline. `terragucci promote` and `terragucci rollback` first read `.chant/pipeline.ts` on the default branch and exit 1 unless it gates the environment, so push the pipeline with the components. A promote asks before it plans, so `gate: on-destructive` asks on every promote. A rollback into a stage that sets `pause_after_rollback` pauses the stage until `terragucci resume`. When `.chant/pipeline.ts` is the repo's own, `init` keeps it and gives the components a gate for each environment that waits. Under `release.green: forge-checks` the release the last wave cuts also counts the `check` job and the earlier wave jobs of its own run. The workflow `init` writes passes those jobs to `terragucci waves-spec --own-run-jobs` ([Promote a release through environments](/terragucci/guides/promote-a-release/)).

The drift agent's jobs are now chant's `terragucci-drift-agent` and `terragucci-drift-agent-push` in `terragucci-drift.yml`. The agent's pull request comes from the branch `terragucci/agent/terragucci-drift`. A drift run that opens the drift issue now runs `terragucci drift-agent show`, which lists each drifted resource with the state's value and the live one (never a sensitive one). The agent's prompt therefore holds what drifted and not only how many resources did. The drift job ends green with a `drift` output, and the `terragucci-drift-found` job that chant renders beside it shows the run red on drift ([Have an agent fix drift](/terragucci/guides/agent-fix-drift/)).

`terragucci install`, and the install a stage runs for a root that pins its own version, now work in a job whose user cannot write the install directory. That is the Chainguard set's user 65532 when `TOFU_INSTALL_DIR` is a cache directory the runner mounts as root. A release the directory already holds is used where it is. Otherwise the install goes under `$HOME/.cache/terragucci-bin`, or the temp directory's `terragucci-bin` when `$HOME` cannot be written, and the job's log says so in one line. It refuses only when the job's user can write none of them, and names the directory, the user and the remedy. The check happens before the download. A job that can write the directory, such as every job in the Debian set, installs there as before, so a runner that keeps it still shares each release between jobs.

A wave that reads the state of a root an earlier wave applied now reads that wave's plan from the report its job handed on, on GitHub and Forgejo from the artifacts a wave's job downloads and on GitLab from the previous job's `terragucci-report/`. Before, with each wave in its own job, a repo without a `reports` bucket found no plan of the upstream, so the reading wave waited for an approval under `gate: on-destructive` even when every output it read was known at plan. It waits now only when the upstream's plan left an output it reads unknown ([Linked roots](/terragucci/concepts/waves-and-approvals/#linked-roots)).

## In 0.4.65

chant moves to `0.124.115`, in the package and in the images it builds.

Each release now publishes the four CI images in two sets, eight in all. The package records the digest of every one. The Debian set is as before: `node:22-bookworm-slim`, apt, running as root. It runs Node `22.23.5`. The new Chainguard set is built on Chainguard's public `node` and `wolfi-base` images. It installs with apk and runs as user 65532. Its Node is the one Wolfi packages, `26.13.1` when the set was built, so a later release can move it to a newer major. Both sets carry the same engines at the same versions. The Chainguard tags end in `-chainguard` and share a repository with the Debian ones, and each image's labels record its base. The apk packages in the Chainguard images are installed at the versions chant pins, so they move with chant's pins.

`image.base` in `terragucci.yml` picks the set: `debian` (the default) or `chainguard`. `image: { base: chainguard }` is enough with no `name`, and `init` writes the pipeline with that set's image by digest. `image recipe` builds `FROM` the set `image.base` names. Its steps run as root and the image ends as the user the base runs as, so a layer of your own on the Chainguard base wraps its changes in `USER root` and `USER 65532` and installs with apk. [Run the jobs in a prepared image](/terragucci/guides/run-in-a-prepared-image/#the-two-image-sets) and [Versions and pins](/terragucci/reference/versions-and-pins/#the-two-image-sets) compare the two sets. A release before this one published only the Debian images and refuses `image.base: chainguard`.

terragucci's own release now runs with chant's `supply-chain` group on. It refuses a base image named without a digest and scans each image before anything is pushed. Each image gets an SBOM made from its layers and a keyless Sigstore signature. It also gets SLSA provenance, which the publish requires. The npm package carries an SBOM as well, and its scan covers the packages an install brings in, with no development dependencies.

The CI images move to engine releases built with a Go toolchain and Go modules that fix the critical vulnerabilities a scan finds in the older binaries:

| Engine | Was | Now | Image tag |
|---|---|---|---|
| OpenTofu | `1.13.1` | `1.13.9` | `<version>-tofu1.13.9`, and `<version>-tg1.2.0-tofu1.13.9` for the Terragrunt image |
| Terraform | `1.14.9` | `1.17.2` | `<version>-tf1.17.2` |
| choudoufu | `0.31.0` | `0.35.0` | `<version>-choudoufu0.35.0` |
| Terragrunt | `1.2.0` | `1.2.0` | unchanged |

A root that pins its own version still runs that version, which the job installs. So a root that has to stay on Terraform `1.14.9` pins it in `.terraform-version` or `required_version`. The image build checks each new release against the sha256 terragucci records for it and against the release's checksums file.

The npm package's SBOM lists vitest `4` in place of vitest `3` and no longer lists tinypool `1.1.1`.

## In 0.4.64

chant `0.124.112` is the pin for the package and the CI images.

`promotion: [dev, staging, prod]` in `terragucci.yml` names the order a release moves through the environments. `terragucci promote` applies a release to the next environment behind that environment's gate, and `terragucci rollback` brings an earlier release back the same way. `terragucci approve release <env>` approves a waiting one. A promote that skips an environment needs `--allow-skip`, and `--urgent --reason <text>` passes the stage's gate on its urgent rule with the reason on the stage's ledger. Each promote or rollback records the release the environment runs on `chant/lifecycle`. `init` writes `terragucci.component.ts`, which holds each root as one chant component. The merge applies the first stage and cuts the release that later stages promote; `release.cut: false` turns the cut off. [Promote a release through environments](/terragucci/guides/promote-a-release/) walks through it.

Under `promotion`, `init` writes `release: { green: "forge-checks" }` into `chant.config.ts`, so the cut on merge waits for the merge commit's checks on the forge. On GitHub the wave jobs get the `checks`, `statuses` and `actions` read permissions for that. A pull request's plan runs in the first stage's environment, and its plan jobs and note jobs name that environment where they named `default`.

Each environment under `environments.<name>` takes chant's stage keys, such as `approval`, `approval_rules`, `hold`, `freeze`, `soak`, `canary`, `risk` and `hooks.<when>`; the [Stages](/terragucci/reference/config/#stages) section lists them all. `terragucci ci` writes `.chant/pipeline.ts` from them, and `--check` fails on a stale file. A stage's first wave is its canary when `waves.canary` names every root in it and its soak has a check. `risk.approve_above` holds a wave over the score. The wave's risk record is `input.risk` in the policy and `waves[].risk` in the report. `terragucci reject`, `terragucci pause` and `terragucci resume` run chant's commands of those names.

`rollouts.soak` runs on chant's wave soak with its keys unchanged, and it also takes chant's `duration` and `checks` with `kind` and `on_fail`. A wave holds while a check finds drift, and the apply and policy checks hold it the same way. `/terragucci skip-soak` is recorded as the approval of the wave's soak gate with the commenter's name.

Agents start on a trigger, and each is off until its key is set. `agent.alert` answers a production alert and `agent.apply-failed` a failed apply. `agent.verify-failed` answers a failed verify or soak, and `agent.schedule` runs on a `cron`. `init` writes one workflow per agent beside the pipeline, and run records carry the `trigger`. The [agent from an alert guide](/terragucci/guides/agent-start-from-an-alert/) points each alert source at chant's relay.

`terragucci.yml` reads the keys of chant's product vocabulary and still reads each earlier spelling. `gate: on-destructive` replaces `on-destroy`, and `identity` replaces `oidc`. `branches.<branch>` takes over from `apply.branches` and `forge_url` from `url`. `locks.when`, `drift.schedule` and `notify.relay_name` replace `locks`, `drift` and `notify.relay`. `terragucci config check` warns once for each earlier spelling it reads.

The cost estimate is chant's. chant runs `cost.command` (Infracost by default) over each root whose plan changes something and writes the cost section of the plan note, with a row per root. A root whose plan changes nothing is no longer priced. The command still reads the redacted plan from `TG_PLAN_JSON` and the root from `TG_ROOT`, and it still runs without the forge tokens. The `cost` keys in `terragucci.yml` are unchanged.

With `cost.approve_above`, the waves' spec carries chant's cost hold, which prices the wave, holds it over the amount and gives the `(monthly cost)` member of its digest. That member's digest is chant's now. The hold runs the command with chant's redaction, which covers what the plan marks sensitive, so declare each variable that takes a `secrets:` value `sensitive = true` ([Another estimator](/terragucci/guides/estimate-cost/#another-estimator)). A wave that waited on its cost before the upgrade waits for an approval of its new digest, so approve it again with `terragucci approve`.

The policy's `input.cost` is chant's record, with fields such as `monthlyDelta`, `members` and `approveAbove`. The earlier fields `input.cost.root`, `input.cost.wave` and `input.cost.approve_above` sit beside them, so existing policies keep working. [Policy](/terragucci/reference/policy/#cost) pairs each with chant's field. `run.cost_estimate` under `input: hcp` is filled as before.

`respond.wave-refused: summary` puts a model's summary above the diff in the note on a refused wave. chant's wave job runs it with the `agent.wave-refused` keys. [Have an agent summarize a refused wave](/terragucci/guides/agent-refused-wave/#move-from-an-explain-refusal-job) shows how a repo with the `explain-refusal` job under `own_jobs` moves to it.

The reports bucket's files are in chant's report-store format, which every CI product on chant writes. `report.json` and `run.json` are `chant.run/v1`. `estate.json` is `chant.estate/v1` and `dora.json` is `chant.dora/v1`. Each names `product: "terragucci"` and keeps its body. Each new line of `audit.jsonl` is `chant.audit/v1`: chant's word for the event is in `kind` and terragucci's in `product_kind`. Lines already in the record stay as they are, and terragucci reads both forms. `index.json` stays `terragucci.report-index/v1`. [Reports bucket](/terragucci/reference/reports-bucket/#json-schemas) lists the new ids, and the [audit trail](/terragucci/reference/audit-trail/#query-the-record) has queries for the new lines.

## In 0.4.60

The npm package and the four CI images now carry chant `0.124.98`.

A `roots` glob leaves out a directory that a root calls as a local module and that has no backend or `cloud` block of its own. Name it by its exact path to keep it. `terragucci config check` says how many matched directories were left out.

`terragucci init` and `config check` name each root whose `required_version` range excludes the version its job runs, with the `version` entry that fixes it.

A root takes its own `-backend-config` and `-var-file` files with `backend_config` and `var_files`, each a map of root globs. One directory can run as several roots with `instances`. Each instance is a root named `<directory>@<name>` with its own data directory. `terragucci import atlantis` writes these from a project's `extra_args`.

`sources` can be a map of root globs, so each root allows its own sources. The map needs a `default` list, and a root that a pull request adds gets that list. The threat model page has a section on what runs at plan time and which of it `sources` stops.

`terragucci pin modules` and `terragucci pin providers` turn version ranges into the exact versions `init` resolved, and open the change as a rollout whose plans show no change. A call with no version gets one where the edit is safe. `--dry-run` prints the table.

`rollouts` can now be a map. `rollouts.watch` starts a rollout when a module or provider it follows has a newer release, with `follow` and `min_age` per rule, and a Renovate or Dependabot pull request for the same version counts as the canary. `rollouts.soak` holds the next wave until the one before it has soaked. It can also wait until the wave has no drift and no failed apply. A person with write access can skip it with `/terragucci skip-soak`. `terragucci estate` shows how far behind each module and provider version is.

`terragucci import atlantis` finds `.atlantis.yaml` on its own and follows `autodiscover`. It leaves out module directories and names each project's `workflow`.

`runtime: prow` writes the stages as Prow jobs. Plan and apply run as postsubmits and drift as a periodic job. The check presubmit holds no credential, and `plan_before_merge` adds a plan presubmit. With `approval: prow-labels` a wave applies once it has `lgtm` and `approved` from someone outside the change, and its plan matches the plan note. The plan and apply stages run as different service accounts, and `config identities` names each stage's pod identity.

`comment_allow` limits the comment commands to logins and `team:<org>/<team>` entries, read from the default branch. On GitHub and Forgejo it covers `plan`, `apply`, `lock`, `unlock`, `agent`, `action` and `skip-soak`. On GitLab it covers every command but `action`. A team the token cannot read stops the command with a message. `TG_TEAM_TOKEN` is passed to the jobs that read teams, only when a team is named.

`terragucci modules adopt <dir>` moves each local call of a module to its published source, caller by caller, as a rollout. Each wave's plan shows no change.

`modules.attest: { identity: oidc }` signs modules with the publish job's OIDC identity, with no key. A `modules.trusted` entry can trust an `identity: { issuer, subject }` in place of a key.

A new page, Repository dependencies, says what a repository depends on after `init`. It covers what `init` writes and every outbound call, and how to stay on a pinned release or leave.

## In 0.4.59

Both the npm package and the four CI images now carry chant `0.124.95`.

The plan jobs are chant's product plan jobs now. Their names, their check and their report artifacts stay as they were. An open pull request gets one new plan note after the upgrade.

On GitLab the plan job holds no token. A plan notes schedule posts the notes instead. It runs every five minutes with `CHANT_PLAN_NOTES=1` and `TERRAGUCCI_SCHEDULE=plan-notes`, and `terragucci init` names it. `gitlab.token: protected` no longer needs `comments`. The commands `terragucci oidc-trade` and `terragucci post note` are gone.

A migration whose state moved after an earlier approval now waits for approval under the new digest. It used to refuse and name the roots.

`terragucci state export` names its requester through chant's `actorOf`. The order it reads them in is the same.

`terragucci registry edge` writes its Worker or Lambda@Edge files through chant's planned files. A rerun leaves an unchanged file alone.

terragucci runs its engine binaries through chant's engine runner. chant traces the commands, so terragucci's own command tracing is gone.

A Terragrunt unit's binary spans now sit under a `<binary> plan` span under `root <unit>`. They are timed from Terragrunt's run report. A unit missing from that report gets a `<binary> plan` span with exit -1 and says it did not run.

Every run of the binary now gets `TF_IN_AUTOMATION=1`. In a Terragrunt repo `terragucci plan` uses chant's Terragrunt runner.

The new `evidence` key signs the plan and wave checks, and `terragucci init` writes `.chant/trust.json` with the ref gate's rule.

`terragucci run wave` runs one job of chant's Op waves pipeline with terragucci's hooks in the job's process.

`terragucci waves-spec` prints the `tf-apply` waves spec at a commit. It reads the spec file and `terragucci.yml` committed there.

The apply waves now run on chant's Op waves jobs. Each of them runs `terragucci run wave` and reads its rules at base through `terragucci waves-spec`. Every repo shape now commits `.chant/op-waves/tf-apply.spec.json`. Run `terragucci init` to write the pipelines again.

Job names and the required checks stay as they were, and so do the report artifacts. After each wave comes a status job, and the last one is `apply-done`. Plan notes a push made stale are flagged by the new `stale-notes` job. The `terragucci/apply` descriptions now come from chant.

GitLab's `mr-apply` job is gone, with its artifact `terragucci-report-mr-apply`. The artifacts `terragucci-report-apply-comment` and `terragucci-report-resume` are gone too. Before merge chant splits each wave into four jobs, so the change's code never runs beside a write token.

Wave jobs take chant's defaults for every product. That means a 180-minute timeout and the full history. The checkout pin is chant's too.

With `runner.apply` set, `pr-merge` and `control` move to the apply runner along with `stale-notes`. The comment job stays on the default runner, since it applies nothing now.

The control dispatch keeps its concurrency group. GitLab's resume keeps its resource group.

The rest of a stopped apply now applies only at the commit it stopped at. A push in between waits for a new approval, where terragucci used to take it up at any commit. chant ties an approval to the code it approved.

Let a killed apply on Forgejo finish or resume before you upgrade. chant does not read the `kind: "changes"` lines terragucci wrote.

`/terragucci apply` now runs as chant's comment job. On a merged pull request it starts the failed wave jobs again. Before merge it decides the head and starts the waves for it. That replaces the `control-comment` job.

With `apply.when: pull-request`, chant answers `/terragucci lock` and `/terragucci unlock` too. `/terragucci apply` takes the same locks as it decides the head, through the new `terragucci reach`. A member of a control repo that applies before merge tells it once the merge is pushed.

The commands `terragucci comment-apply`, `terragucci pr-merge` and `terragucci resume` are gone, since chant's jobs do that work.

The wave jobs get the notify secrets under the names `terragucci.yml` gives them. `TERRAGUCCI_RELAY` and the `TERRAGUCCI_*_WEBHOOK` variables are gone from them. The hooks read the forge's own variables now, so `TG_TOKEN` and `TG_SHA` are gone as well, with `TG_BEFORE` and `TG_BRANCH`.

## In 0.4.55

Under it is chant 0.124.81, pinned by the package and by each CI image.

A control repo keeps its projects and defaults only as chant's entries on its `chant/lifecycle`. The record files under `terragucci/records` are no longer read, and `terragucci control records init` is gone.

- 0.4.54 is the last release with `terragucci control records migrate`. A control repo that still has record files runs `npx @intentius/terragucci@0.4.54 control records migrate` and pushes `chant/lifecycle`. Then it upgrades.
- `control records put`, `defaults`, `import` and `retire` write the entries on `chant/lifecycle` from the first one, so a new control repo needs no setup step.
- The plan job reads the control repo through chant's read step alone. On GitHub and Forgejo it no longer checks the control repo out into `.terragucci-control`, and on GitLab it no longer clones it. `TERRAGUCCI_CONTROL_DIR` is no longer set by the job, though a plan still reads a checkout it names.
- `TERRAGUCCI_CHANT` is no longer read.
- A plan that reads the control repo through `TERRAGUCCI_CONTROL_READ_TOKEN` now finds its estate owners. The clone it read was removed before the read finished, so it found none.
- The review agent reads the pull request, the pipeline's runs and jobs, and the review artifacts through chant's forge reads. A review artifact whose run the forge no longer lists is passed over, and the log says so.

On GitLab, the comments schedule answers merge request notes through chant's note commands:

- Who may ask is read as a role. A note from below Developer is ignored, and the job's log names that role.
- A reply ends with the user it ran for. What terragucci adds, such as that the job reads the merge request again, comes before that, in parentheses.
- `/terragucci apply` on a merged merge request retries in the newest push pipeline at its merge commit that has an apply job, in chant's words. A later commit with the apply status still refuses it.
- A note whose change cannot be compared in full gets no reply, and the next poll reads it again.

Every wave now plans and applies on chant's step, and terragucci's own wave plan and apply are gone:

- A wave whose roots pin their own releases. chant runs the release each root pins once terragucci has installed it and checked its version. The binary in `chant.config.ts` no longer matters, and a repo with no `chant.config.ts` plans each root by its directory.
- A wave under `approval: pr-review` or `approval_rules` runs on the step. chant decides its gate and counts the review terragucci records. It leaves out the people behind the change and the agent's account, and it counts `approval_rules`. The report's rules and review come from that decision.
- With `agent.token_env` and no `agent.login`, the job leaves out the account the agent's token acts as.
- An Atmos read of another instance's outputs is read from that instance's own workspace, with its role and its pinned release.
- `--parallelism` and `parallelism` run a wave's roots side by side as before. Their inits take turns on the wave's provider cache, and the job says how many roots run at once.
- The binary each root runs still sees no forge token, whether named as one or holding the same value.
- A root an estate migration adopts into is left out of its wave until the migration has applied, and the next run plans it.
- chant records a pull request's approving review itself. Each reviewer is named by forge principal, such as `github:alice`.
