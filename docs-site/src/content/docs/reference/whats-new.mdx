Release `0.4.53` is on npm as `@intentius/terragucci@0.4.53`, and its [GitHub release](https://github.com/INTENTIUS/terragucci/releases/tag/release/0.4.53) lists every change.

| To upgrade | Run |
|---|---|
| Each repo | `npx @intentius/terragucci@0.4.53 init`, then merge the pipeline it writes, with `chant.config.ts` in a repo of plain roots |
| Each approver | `terragucci approve` where you ran [`chant approve`](/terragucci/concepts/glossary/#chant); installing terragucci is enough ([approve](/terragucci/reference/cli/#approve)) |

## In 0.4.56

The package and each CI image now pin chant 0.124.87.

`terragucci notify relay` refuses a click when the signers file's history at the default branch doesn't verify, such as a signer added straight to main without a signed rotation, and records nothing. A repository that added a signer that way adds it again with `chant workspace signers rotate`.

The release workflow's gate stops at once when the newest green commit's workflow files differ from the dispatched commit's, and the publish job retries an image upload GHCR refuses.

A wave's report has each root's plan and apply seconds, span count and lock waits again, read through chant's hook around each engine command.

The drift issue is chant's. Its body is chant's table of what drifted, with terragucci's attributions and the roots that failed to read as notes, and drift that hasn't changed no longer edits the open issue. Each open drift issue is edited once on the first run after the upgrade.

State migrations plan and write through the terraform lexicon. A migration request asked before the upgrade and approved after it is asked again, since its digest changed. A migration on GitLab-managed `http` state now runs, where terragucci refused it before.

A GitLab project with no drift schedule gets chant's warning, which names the `TERRAGUCCI_SCHEDULE` selector. A plan note on GitLab is cut at 1,000,000 characters, the limit chant uses.

In the CI images, each engine is checked against its release's checksums file and the sha256 terragucci or chant records. A build for an architecture with no recorded sum fails, and the engines are installed under `/opt/terragucci/<tool>-<version>/` and linked into `/usr/local/bin`.

## In 0.4.55

Under it is chant 0.124.81, pinned by the package and by each CI image.

A control repo keeps its projects and defaults only as chant's entries on its `chant/lifecycle`. The record files under `terragucci/records` are no longer read, and `terragucci control records init` is gone.

- 0.4.54 is the last release with `terragucci control records migrate`. A control repo that still has record files runs `npx @intentius/terragucci@0.4.54 control records migrate` and pushes `chant/lifecycle`. Then it upgrades.
- `control records put`, `defaults`, `import` and `retire` write the entries on `chant/lifecycle` from the first one, so a new control repo needs no setup step.
- The plan job reads the control repo through chant's read step alone. On GitHub and Forgejo it no longer checks the control repo out into `.terragucci-control`, and on GitLab it no longer clones it. `TERRAGUCCI_CONTROL_DIR` is no longer set by the job, though a plan still reads a checkout it names.
- `TERRAGUCCI_CHANT` is no longer read.
- A plan that reads the control repo through `TERRAGUCCI_CONTROL_READ_TOKEN` now finds its estate owners. The clone it read was removed before the read finished, so it found none.
- The review agent reads the pull request, the pipeline's runs and jobs, and the review artifacts through chant's forge reads. A review artifact whose run the forge no longer lists is passed over, and the log says so.

On GitLab, the comments schedule answers merge request notes through chant's note commands:

- Who may ask is read as a role. A note from below Developer is ignored, and the job's log names that role.
- A reply ends with the user it ran for. What terragucci adds, such as that the job reads the merge request again, comes before that, in parentheses.
- `/terragucci apply` on a merged merge request retries in the newest push pipeline at its merge commit that has an apply job, in chant's words. A later commit with the apply status still refuses it.
- A note whose change cannot be compared in full gets no reply, and the next poll reads it again.

Every wave now plans and applies on chant's step, and terragucci's own wave plan and apply are gone:

- A wave whose roots pin their own releases. chant runs the release each root pins once terragucci has installed it and checked its version. The binary in `chant.config.ts` no longer matters, and a repo with no `chant.config.ts` plans each root by its directory.
- A wave under `approval: pr-review` or `approval_rules` runs on the step. chant decides its gate and counts the review terragucci records. It leaves out the people behind the change and the agent's account, and it counts `approval_rules`. The report's rules and review come from that decision.
- With `agent.token_env` and no `agent.login`, the job leaves out the account the agent's token acts as.
- An Atmos read of another instance's outputs is read from that instance's own workspace, with its role and its pinned release.
- `--parallelism` and `parallelism` run a wave's roots side by side as before. Their inits take turns on the wave's provider cache, and the job says how many roots run at once.
- The binary each root runs still sees no forge token, whether named as one or holding the same value.
- A root an estate migration adopts into is left out of its wave until the migration has applied, and the next run plans it.
- chant records a pull request's approving review itself. Each reviewer is named by forge principal, such as `github:alice`.
- A choudoufu wave that meets a resource another live run is applying ends at once with exit 5. A push's wave used to wait for that run.
- A stock binary's root is held as one row of `pr-apply` while it applies.
- The wave's report has no per-root plan or apply times and no spans, and a failed root's outcome names no error.
- A Terragrunt repo's waves run on chant's `terragrunt-apply` step. Each wave still plans its units with one `run --all` per pair of releases, and applies exactly those saved plans.
- With `waves.compose`, the composed run is chant's: its wave lists the run's roots, and chant plans and applies them together as one run. That run keeps the binary the project names.
- A gate whose only change is an output now waits for an approval, where before it let the wave through as empty.
- A share job applies its saved plans even when they change nothing.
- A root that names its workspace plans and applies in it on the step. Its init runs in `default`. Then the workspace is selected, and created first when the backend does not list it yet.

## In 0.4.54

This release pins chant 0.124.79 in the package and the CI images.

- Every record terragucci writes on `chant/lifecycle`, such as a state export, a lock release, a migration, an agent run or a template request, goes through chant's ledger writer. In a checkout with no remote the record stays on the local branch, where the command used to fail.
- A choudoufu wave holds its resources only through chant's row leases, in `_locks/rows/pr-apply.json`; `_locks/apply-rows.json` is no longer read or written. Whether a holding run is gone is chant's answer too: a holder that keeps a heartbeat is judged by it, and `CHANT_LOCK_STALE` and `CHANT_FORGE_TOKEN` are read before `TG_LOCK_STALE` and `TG_TOKEN`.
- `terragucci state export` and `terragucci unlock-state` run on chant's state export and lock release. An export is refused in a CI job and into any git working tree, and a request that was exported already exits 1. `unlock-state` exits 5, not 1, when a run that may hold the lock is still alive, and 1, not 4, for a request that released already; a new lock is a request of its own, which waits for its own approval.
- A pull request's ephemeral copy is planned, applied and destroyed by chant's pull request environments of Terraform roots, with the same state key suffix and records. An azurerm copy's location is now recorded as `az://<account>/<container>/<key>`; copies recorded before are still destroyed.
- terragucci reads pull requests and who may comment through chant's forge reads. On GitHub, a comment whose author's permission the job's token cannot read is ignored as one without write access; the job no longer fails on it. A rollout no longer takes a pull request from a fork for one of its waves.
- On GitLab the overdue drift check asks chant which schedules are drift's, by the drift job's own rule. That rule now always leaves out the `comments`, `resume`, `rollouts` and `ephemeral` schedules, whichever of those the config turns on.
- More waves plan and apply through chant's `terraform-apply` step. `secrets`, `cost` and `ci.hooks` no longer keep a wave on terragucci's own plan. Nor does a choudoufu root, or a read of another root's state.
- Each root on the step runs the binary `chant.config.ts` names, from the directory of the job's binary or of the version the root pins. A root that plans with another binary keeps terragucci's own plan, and the job says why. So does a wave under `approval: pr-review` or `approval_rules`.
- A wave on the step plans its roots one at a time. Each root's plan file is `chant.tfplan` in its own directory.
- `terragucci mcp` lists each tool's MCP annotations, as its own server did before it moved onto chant's. `plan_result` is the one change: it is listed as not read-only, since it is served with the propose tools.
- An MCP tool that answers with a list, such as `index` or `templates`, now gives it as `structuredContent.items`. Its text block still holds the list.
- A release takes its version from its label: the publish run stamps it into the package for its build, and each image's version label comes from the build. main keeps its committed version, and a release no longer needs a commit that moves it.

## In 0.4.53

On chant 0.124.76, the drift check, the formatting commit, the chat relay and the release itself run as chant's jobs, so terragucci no longer writes its own.

- The drift check is chant's drift Op in a workflow of its own on every forge. Run `init` and merge what it writes; a run that finds drift without `agent.drift` now stays green.
- The formatting commit is chant's commit job. It starts only when the check finds formatting (exit 3), and it never pushes to a head whose plan is already approved.
- Approving from chat needs `notify.relay_key` set to the variable that holds the relay key ([approve from chat](/terragucci/guides/approve-from-chat/)). A Teams reply is now `approve <reference>`.
- `dora.json` is built by chant's delivery code from the same records, and keeps its fields and values.
- A release is cut and published by chant in one run under the tag `release/<version>`, which pushes the images, publishes the package and makes the GitHub release together.

The three releases before this one were tagged but never reached npm, while chant's release jobs learned what a repository's first release needs: the cut's images handed to the publish job, and the token the GitHub release is made with.

## In 0.4.49

With chant 0.124.58 underneath, requesting an app or an add-on from a template, gated day-2 actions, requests from an agent and upgrade waves all run through chant, so terragucci drops the fallbacks it kept for an older chant. Each of those has a published guide now.

## In 0.4.47

The package and the CI images move to chant 0.124.57, and more of what terragucci did itself is done by chant.

- A wave with nothing keeping it back plans and applies through chant's `terraform-apply` step. Such a wave waits for its root's row on chant's ledger, and its run and release records are pushed again when another job pushed first.
- `terragucci check-job` is chant's job guard. A job that runs where its stack is not set to apply exits 9 (`misplaced`) and runs nothing. On GitHub the job's token is asked for the `chant-check-job` audience.
- Drift attribution reads CloudTrail and the known writes through chant's audit log reads. The unrecorded writer audit is still terragucci's.
- terragucci no longer keeps its own copies of chant code such as the comment words. Each of those parts behaves as chant's does.

## In 0.4.46

This release is built on chant 0.124.55, whose wave runtime the CI images carry, and much of what terragucci carried itself now comes from chant.

- Exit codes are chant's table: 0 done, 1 failed, 2 drift, 3 waiting, 4 moved, 5 held, 6 superseded, 7 denied, 8 declined. A usage or config error now exits 1, where it exited 2. `stage tf-apply` passes chant's 7 and 8 through, where it gave 1 and 4. [Exit codes](/terragucci/reference/cli/#exit-codes) lists each command's.
- When a repo has plain roots, `init` also writes `chant.config.ts` and `.chant/op-waves/tf-apply.spec.json` for chant. Each wave then plans and applies through chant's `terraform-apply` step.
- A composed run (`waves.compose`) is chant's. Its temporary root is `.chant-compose/`, and a state it could not write is kept as `<key>.chant-unwritten`. chant can leave a root out of the run and compose the rest; the note and `compose.left_out` in the report name each root left out with its reason.
- `modules.publish` takes a GitLab module registry (`gitlab`), HCP Terraform (`hcp://<organization>`) and Artifactory or Nexus. `terragucci registry edge` writes an edge function for a bucket-hosted registry, with an optional token check. `modules.registry.providers: mirror` serves providers from the same registry. See [Publish modules](/terragucci/guides/publish-modules/).
- Each release is recorded on chant's ledger and listed in a release catalog beside the registry, which `terragucci modules` reads. `modules deprecate` and `modules yank` mark a version, and `modules restore` clears the mark. Roots on a deprecated version get the `terragucci-deprecated-version` tip, and `modules.require: attested` refuses a yanked pin.
- `sources.proxies` names an Artifactory or Nexus registry proxy, so a source written through it matches the entry for its upstream.
- `check.pre_commit: true` runs the repo's `.pre-commit-config.yaml` in `tf-check` ([Run your pre-commit hooks in CI](/terragucci/guides/run-pre-commit-hooks/)).
- A choudoufu root's derived record store is read wherever its state was. The estate page and the `terragucci-module-table` tip give each module version's row in choudoufu's module table.
- State exports, lock releases and migrations record their approvals as chant's gated requests, in `_gates/<op>/applied.jsonl` on `chant/lifecycle`, with the digest of what each one wrote.
- The CLI bundle imports chant core from the installed `@intentius/chant` instead of carrying it.

## In 0.4.43

- Ephemeral environments run on chant's pull request environments (#1228). A copy's plan that changes something now waits for an approval whatever `gate` says, so `gate: on-destructive` and `gate: never` no longer let a copy that only creates resources apply on its own. A plan with nothing to change applies without one. `terragucci approve ephemeral <n> --plan <digest>` is still the command; it now runs `chant approve pr-<n> pr-env --plan <digest>`, and the approval is kept in `_gates/pr-<n>.jsonl`. The copies are recorded in `_pr-envs/records.jsonl` on `chant/lifecycle` instead of `_gates/tf-ephemeral/done.jsonl`. terragucci still reads the old file, so a copy applied before you upgrade is destroyed on close or at expiry as before. A destroy that fails is tried once more in the same run, and its audit entry counts the roots destroyed instead of carrying the destroy plans' digest.

## In 0.4.41

terragucci now runs on chant 0.124.42 and uses chant's own versions of the CI features it used to carry (INTENTIUS/chant#4287). Most config keys read as before. These are the changes you can see:

- `steps:` is gone. Move each one to `ci.hooks` in [`chant.workspace.json`](/terragucci/concepts/glossary/#chantworkspacejson); `config check` refuses `steps:` and says where each one went (#1220). chant's stage-hook runner runs them, so when roots plan side by side their hooks now take turns (#1225). Each hook's environment gains the `CHANT_WAVE*` variables and `CHANT_HOLD`.
- `approval_rules` keeps its keys and is judged by chant's `approvals.quorum` rule (#1217). A reviewer is matched by their full forge principal now. A grant to a bare login no longer gives that reviewer a role, and neither does a `gitea:` grant or a `github:` grant on another host. The approvals guide covers the migration under "A reviewer's roles".
- `apply.requires` runs chant's four requires checks (#1226). A refusal lists every check that failed. `approved` also leaves out anyone who wrote a commit in the change. `checks` needs at least one status to have reported. `undiverged` is read from the forge. A forge API error gets a refusal reply instead of failing the job.
- `apply.branches` uses chant's branch routing (#1212). A root that matches two branches is refused by `config check` and by the apply job. Its globs follow picomatch, so `envs/prod/**` also matches `envs/prod` and `*` skips a name that starts with a dot.
- Root locks now come from chant's target locks (#1216). The overdue drift check uses chant's scheduled-Op verdict (#1221), and a failed root blocks its dependents through chant's wave-blocked rule (#1222). Their config is unchanged.
- Under `opa`, the policy engine counts packages one level under the namespace, so a deny in `main.<child>` now fails the root (#1218).
- The re-plan trades its OIDC token with chant's trade before it checks out the head (#1213). `terragucci query` uses chant query's statement check (#1214). The review command and risk line come from chant's review agent (#1224).
- A step that runs the change's code also drops `CHANT_*_TOKEN`, `GITLAB_TOKEN` and `CI_JOB_TOKEN`. A restarted step carries `CHANT_NO_FORGE_TOKEN` in place of `TG_NO_FORGE_TOKEN` (#1219). Run `init` to pick up the new pipeline.
- Terragrunt 1.2.0 is in the image. Dependency outputs are read through the binary, and expanded stack `unit` blocks are refused (#1209). `oci://` unit sources are pinned and checked, and the azurerm backend bootstrap works (#1211).
- `publish` pushes an OCI module as one `archive/zip` layer and republishes versions that were pushed as a tar (#1210).

## In 0.4.40

- A wave's gate is the stricter of the pipeline's `--gate` and the top-level `gate` in `terragucci.yml` at base, as every other hold key already was (#1202). A pull request that loosens `gate` applies its own merge under the old gate, its plan note says so, and the new gate takes effect from the next merge. One that tightens `gate` takes effect on its own merge. When the config at base cannot be read, a wave under `gate: never` does not apply. The apply jobs can now write [`chant/lifecycle`](/terragucci/concepts/glossary/#chantlifecycle) under every gate, so run `init` to pick up the new pipeline.
- `terragucci init --gate never|on-destructive|always` writes `gate:` into `terragucci.yml` and renders the pipeline with it. A config that already sets another gate makes `init` exit 2 unless you pass `--force` (#1201). The agent setup prompt asks whether waves should wait for an approval.
- A new guide, [Run without approvals](/terragucci/guides/run-without-approvals/), covers `gate: never`, the holds that still wait under it, and keeping the plan identity read-only (#1203).

## In 0.4.39

- On GitHub, the `check`, `plan` and `replan` jobs end with the step that runs the change's code, as they do on Forgejo, so no later step in those jobs holds an API token (#1193). The report goes to the next job as job outputs, which GitHub caps at 1 MB: a plan report over about 330 KB gzipped reaches the note as the note, the status, `report.json` and `drift-schedule.json`, and a reports bucket still keeps all of it.
- Each applied root's binary, provider and module versions go to `versions.json` in the reports bucket and to `roots[].versions` in the report. The estate page lists every version in use with the roots on it, and `terragucci query` has a `versions` table (#1190).
- A change the root's last 3 applied waves each made again folds into its own plan note section, Changes on every run, with the usual fixes beside it (#1189).
- `tf-publish` refuses a module whose version bump is smaller than its interface change, and names each change and the bump it needs (#1191).
- Two tips: `terragucci-secret-in-state`, for a sensitive value in state that a write-only argument or an ephemeral resource could keep out, and `terragucci-choudoufu-secrets`, for a choudoufu root whose records can hold secret values (#1192).
- A later wave's report lists the roots it applied. It used to list none when an earlier wave ran a migration (#1187).
- A migration's `progress.moved` counts each resource once, also when it follows two resources (#1186).
- `terragucci apply` names the run view it writes as a bucket object, `s3://<bucket>/<key>` (or `gs://`, `az://`), not a path that reads like a link (#1184).
- The repository's history before 0.4.38 is now one commit, which keeps a clone to a few megabytes. Every earlier version stays on npm and its pull requests still show each change, but the git tags and GitHub releases before 0.4.39 are gone: pin terragucci by its npm version, not by a git tag.
