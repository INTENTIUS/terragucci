With `policy` in `terragucci.yml`, `tf-plan` fails each planned root whose plan JSON your Rego denies.

```yaml
policy:
  engine: conftest
  path: policy
```

| Key | Default | Meaning |
|---|---|---|
| `engine` | `conftest` | `conftest` or `opa` |
| `path` | `policy` | the directory of Rego files, inside the repo |
| `namespace` | every namespace for conftest; for opa, `main`, or `terraform.policies` with `input: hcp` | the Rego package whose rules count; opa also counts the packages one level under it |
| `input` | `plan` | what `input` holds: `plan`, the bare plan JSON; `hcp`, `{plan, run}` as HCP Terraform's OPA policies read it |
| `source` | none: the repo's own `path` | a shared policy repo at a pinned ref, `git+https://<host>/<path>@<ref>`; see [below](#a-shared-policy-source) |
| `override` | none: no override counts | the forge identities or signers who may let one denied plan through `tf-apply`, read at base; see [below](#overriding-a-denial) |

## A shared policy source

Many repos can share one policy repo. With `source` set, `path` is the directory inside it:

```yaml
policy:
  source: git+https://github.com/acme/policy.git@v3
  path: policy
```

| Part | Meaning |
|---|---|
| `git+https://<host>/<path>` | the policy repo; `git+http://` for a forge on a private network, `git+file://` for a repo on the job's disk |
| `@<ref>` | required: a tag, a branch, or a commit, which pins it exactly |
| `path` | the Rego directory inside the policy repo, default `policy` |

The repo that sets `source` needs no policy directory of its own. Each `tf-plan`, `tf-check` and `tf-apply` job fetches the source at the ref with its own git credentials and logs the commit read. A private policy repo needs a credential the job's git can use, such as a credential helper.

| Case | Result |
|---|---|
| the source cannot be fetched, or the ref is not there | every planned root fails |
| the ref has no `path` directory | every planned root fails |
| a pull request changes `source` | checked against the base's `source`, as for any `policy` key |

### From a control repo

Set `policy` under `defaults` in the [control repo](/terragucci/concepts/control-repo/), or under one project:

```yaml
defaults:
  policy:
    source: git+https://github.com/acme/policy.git@v3
projects:
  github.com/acme/infra: {}
  github.com/acme/network: {}
```

A project's jobs read `policy` from its own `terragucci.yml`, so `reconcile` writes the key there, in a file whose first line says the control repo writes it. `reconcile` fails a project whose `terragucci.yml` sets a different `policy` and names the key to set.

## Writing a policy

A policy is Rego that denies with a message:

```rego
package main

import rego.v1

deny contains msg if {
  some rc in input.resource_changes
  rc.type == "aws_s3_bucket_public_access_block"
  rc.change.after.block_public_acls == false
  msg := sprintf("%s must block public ACLs", [rc.address])
}
```

### Rego input

`input` is the unredacted `show -json` of one root. Before a denial or warning reaches the report, note or log, every sensitive value in it, short ones such as `1` included, becomes `(sensitive, redacted by terragucci)`.

Settings by where the policy came from:

| Policy source | Setting |
|---|---|
| written for terragucci | `input: plan`, the default |
| HCP Terraform OPA policy set | `input: hcp`, with `engine: opa` ([below](#hcp-terraform-policy-sets)) |
| Spacelift | `input: plan`, and change `input.terraform` to `input` in the policy |
| Scalr OPA policy group | `input: plan`, and change `input.tfplan` to `input` in the policy; `input.tfrun` has no counterpart |

HCP Terraform, Spacelift and Scalr policies read other paths and deny nothing as written.

### Cost

In `tf-plan` and every `tf-apply` wave, `input.cost` holds the monthly cost of the root and of its wave when [`cost`](/terragucci/guides/estimate-cost/) is set. Under `input: plan` it sits beside the plan's keys (the plan JSON has no `cost` key of its own); with `input: hcp`, beside `plan` and `run`.

| Field | Value |
|---|---|
| `cost.estimator`, `cost.currency` | the estimator's name, such as `infracost`, and its currency |
| `cost.root.monthly_delta` | the change this root's plan makes to its monthly cost |
| `cost.root.monthly_total`, `cost.root.past_monthly_total` | the root's monthly cost after the plan and before it |
| `cost.wave.number`, `cost.wave.monthly_delta`, `cost.wave.monthly_total`, `cost.wave.past_monthly_total` | the root's wave and the same figures summed over its roots estimated; in `tf-plan`, over the roots the change reaches |
| `cost.approve_above` | `cost.approve_above` in the config at base, or `null` |

A figure the estimator could not give is `null`. Without `cost`, `input.cost` is absent. A denial on cost blocks the plan and the wave like any other, and an [override](#overriding-a-denial) can let one plan through.

```rego
package main

import rego.v1

deny contains msg if {
  input.cost.wave.monthly_delta > 500
  msg := sprintf("wave %d adds %v %s a month", [input.cost.wave.number, input.cost.wave.monthly_delta, input.cost.currency])
}
```

### Review

With [`review.agent`](/terragucci/guides/agent-review-a-pull-request/) set, `input.review` holds the model's review of the pull request a `tf-apply` wave applies, beside `cost`. `tf-plan` runs before the review, so it has none.

| Field | Value |
|---|---|
| `review.found` | whether a run of the default branch's review workflow kept a review of the pull request's head |
| `review.risk` | `low`, `medium` or `high` from that review; `unknown` when none was found, the model gave none, or its command failed |
| `review.pull_request`, `review.head` | the pull request the commit merged, or the one applied before merge, and its head; `null` for a commit no pull request made |

The wave reads, through the forge's API, the newest `terragucci-review-<head>` artifact kept by a run of the default branch's review workflow:

| Forge | Run read |
|---|---|
| GitHub | a `workflow_run` run of `terragucci-review.yml`; the apply jobs get `actions: read` for it |
| Forgejo | a `pull_request_target` run of it whose event names the default branch as the base, and this pull request and head |
| GitLab | none; there is no review job, so `found` is always `false` |

The artifact must say it reviewed this pull request and head against the default branch. The wave passes over an artifact of that name from any other run, such as the pull request's own pipeline, and logs why. It never reads the note on the pull request, since any run's token can post one, a run of another branch included ([threat model](/terragucci/reference/threat-model/#the-review)). An artifact the forge has expired reads as no review. Without `review.agent`, `input.review` is absent.

```rego
package main

import rego.v1

deny contains msg if {
  input.review.risk == "high"
  msg := sprintf("the review of pull request %d says risk high", [input.review.pull_request])
}
```

### Counted rules

| Rule | Effect |
|---|---|
| `deny`, `violation`, `deny_<name>`, `violation_<name>` | fail the root |
| `warn`, `warn_<name>` | warn |
| `hold`, `hold_<name>` | with `hold` in [`outcomes`](#holding-or-releasing-a-wave): the root's wave waits for an approval |
| `allow_unattended`, `allow_unattended_<name>` | with `allow_unattended` in [`outcomes`](#holding-or-releasing-a-wave): the root's plan may apply without an approval |

A message is the rule's string or its object's `msg`. Both engines give the same verdict.

Each denial carries its rule's id, which an [override](#overriding-a-denial) names:

| Engine | Rule id |
|---|---|
| `conftest` | the package and rule of the query that denied, such as `main.deny_public_bucket` |
| `opa` | the package and rule, such as `terraform.policies.no_public_buckets.deny` |
| `opa` with a `policies.hcl` | the policy's name, such as `no_public_buckets` |

The job's log and `roots[].policy.rules` in the report list them.

### Namespace matching

If no Rego file outside the tests declares the namespace and has a `deny`, `violation` or `warn` rule (or, with them in [`outcomes`](#holding-or-releasing-a-wave), a `hold` or `allow_unattended` rule), every planned root is refused and the message lists the packages found.

## Denials

| Case | Result |
|---|---|
| a root's policy denies it | the root fails and the job exits 1; the denials and their rule ids go to `roots[].policy` in the report |
| the policy cannot run (no engine, Rego that does not compile) | the root fails |
| a warning | never blocks |

A denial clears when the code changes until the policy passes, or when the policy changes in a pull request your reviewers approve and merge. A listed approver can also override one plan. Responses, agents and comments cannot waive it.

## Enforcement levels

| Level | Set by | A denial |
|---|---|---|
| Advisory | a `warn` rule; `enforcement_level = "advisory"` in `policies.hcl` | warns and fails nothing |
| Soft-mandatory | a `deny` rule (`mandatory` in `policies.hcl`) | fails the root; a listed approver can [override](#overriding-a-denial) one plan |
| Hard-mandatory | a [hard-mandatory](#hard-mandatory-rules) `deny` rule (`hard-mandatory` in `policies.hcl`) | fails the root; nothing can pass it |

## Hard-mandatory rules

A hard-mandatory rule denies a plan like any `deny` rule, and no override can pass it, whoever `policy.override` lists. Other rules in the same repo stay overridable. The level is set per rule, in either of two places.

In the Rego, put `# terragucci: hard-mandatory` in the comment lines directly above the rule's head. A blank line between the comment and the head cuts the annotation off.

```rego
package main

import rego.v1

# Public buckets are never acceptable.
# terragucci: hard-mandatory
deny_public_bucket contains msg if {
  some rc in input.resource_changes
  rc.type == "aws_s3_bucket_public_access_block"
  rc.change.after.block_public_acls == false
  msg := sprintf("%s allows public ACLs", [rc.address])
}
```

The annotation marks the rule's name in its package (`main.deny_public_bucket`), so every body of that rule shares it. A comment above a `warn` rule does nothing, since it never denies.

In an [HCP Terraform `policies.hcl`](#policieshcl), set `enforcement_level = "hard-mandatory"` on the policy. It denies like `mandatory`.

When a hard-mandatory rule denies a root:

- `tf-apply` records no denial to override, prints no `terragucci override` command, and refuses the wave. The log and the plan note name the rule, as in "main.deny_public_bucket is hard-mandatory: no override, approval or agent action can pass it".
- An override line already on the ledger, or a later one, passes nothing: the wave is refused before the override gate reads it.
- `terragucci override` refuses a `--rule` that is hard-mandatory and names it.
- The refusal is a `refused` entry (`denied-by-policy`) in the [audit trail](/terragucci/reference/audit-trail/), with the hard-mandatory rule ids in `hard_mandatory`. `roots[].policy.hard_mandatory` and `waves[].refused.hard_mandatory` carry them in the report.

The annotation is read from the policy at base, like the rest of the policy, so a pull request cannot remove a rule's level from itself.


## Overriding a denial

With `override` set, a person it lists can let one denied plan through `tf-apply`. The override is a line on the ledger beside the approvals, and it never edits the policy. `tf-plan` still fails the root.

```yaml
policy:
  path: policy
  override: [github:alice, github:bob]
```

<Steps>

1. The policy denies a root in a `tf-apply` wave. The wave applies nothing and exits 1. It records the denial on [`chant/lifecycle`](/terragucci/concepts/glossary/#chantlifecycle) in `_gates/policy-override.jsonl` and prints the command:

   ```text
   envs/prod/app: policy.override at base lists github:alice, github:bob; one of them can let this plan through with:
     terragucci override envs/prod/app --rule main.deny_public_bucket --reason "<why>"
   ```

2. A listed approver reads the plan and the denial, then runs that command in a checkout, with the reason ([`override`](/terragucci/reference/cli/#override)). It records the override with the reason, with `--sign` under `approval: sealed`.

3. Run the wave's job again. Before applying the root, it marks the override used in `_gates/policy-override/applied.jsonl`; its report and note name the override.

</Steps>

### Scoped overriders

A name in the list may override any root's denial, by any rule. An entry instead names who may override the roots its globs match:

```yaml
approval: sealed
policy:
  path: policy
  override:
    - roots: ["envs/dev/**"]
      who: [github:alice, github:bob]
    - roots: ["envs/prod/**"]
      roles: [platform]              # roles from .chant/trust.json
      rules: ["main.deny_untagged"]  # only an override of these rule ids
    - github:carol                   # every root and rule, as before
```

| Key | Means |
|---|---|
| `roots` | root globs; the entry covers a denial of a root one matches |
| `who` | the forge identities or signers it lets override |
| `roles` | the roles in `.chant/trust.json` at base whose holders it lets override; needs `approval: sealed` |
| `rules` | only an override whose rules are all in this list; unset, any rule |

An override counts when a name in the list, or an entry that covers the root and its rules, names the person who wrote it: by name, or by a role `.chant/trust.json` at base gives them. A role counts only under `approval: sealed`, where the override's seal proves who wrote it, so `terragucci config check` refuses `roles` under any other mode. An override of a denial by `main.deny_untagged` and `main.deny_public` counts only under an entry whose `rules` hold both. When a wave holds denied roots of several entries, it refuses an override by someone the entries do not name for that root before anything applies, and says who may override it:

```text
envs/prod/app: the override by github:alice does not count: policy.override at base lets role platform (github:carol) override envs/prod/app for main.deny_untagged
```

A root no name or entry covers is refused as with no `override`. The pull request's plan note and `roots[].policy.overriders` in the report name who may override each denied root.

### Override binding

| Part | Effect |
|---|---|
| one root | every other root's denial stands |
| its plan digest | a plan that changes before the override applied gives another digest: the override counts for nothing, the wave applies nothing and exits 4, and the next run asks again. Once a wave applied under the override, the root's next denial is recorded as a new one and exits 1, waiting for its own override |
| the rule ids | `--rule` names exactly the rules that denied the plan; a rule added or gone needs a new override |
| a reason | required; kept on the ledger line and shown in the report |

### Valid overrides

| Case | Counts |
|---|---|
| by someone `override` lists in the config at base for the root and its rules, written after the wave recorded the denial, with a reason | yes |
| the same under `approval: sealed` | only when sealed by a key the signers file at base lists for that person |
| by someone not listed, listed only for other roots or rules, or listed only by the commit being applied | no |
| a line a job wrote, such as a `pr-review` record | no |
| a line an agent recorded | no |
| no `override` at base | nothing counts, and no denial is recorded |
| a root the policy could not check (no engine, Rego that does not compile) | never overridden |

Base is the applied commit's first parent, or the pull request's base with `apply.when: pull-request`, as for [approvals](/terragucci/guides/approve-a-wave/#rule-commit). Under `approval: ledger` the line names its approver without proving who wrote it; `approval: sealed` proves it ([threat model](/terragucci/reference/threat-model/#policy-overrides)).

### Override records

| Place | Shows |
|---|---|
| the wave's report | `roots[].policy.override`: who, when, the rules, the reason, the plan digest; `policy.overridden` lists the roots |
| the pull request's plan note, and the wave's `note.md` | the override that stands for each denied root, or the command to write one; the plan job still fails the root |
| the estate page | the roots the newest apply waves applied under an override |

## Holding or releasing a wave

`outcomes` lets the policy's rules hold a wave for an approval or let it apply without one, beside denying a root. It needs `engine: opa`: `conftest test` reports only `deny`, `violation` and `warn` rules.

```yaml
gate: always            # for the plans no rule speaks to
policy:
  engine: opa
  path: policy
  outcomes: [deny, hold, allow_unattended]
```

| Outcome | A rule that matches |
|---|---|
| `deny` | fails the root, as without `outcomes`; always on |
| `hold` | `hold` or `hold_<name>`: the root's wave waits for an approval whatever `gate` says |
| `allow_unattended` | `allow_unattended` or `allow_unattended_<name>`: the root's plan is safe to apply without an approval |

A rule matches when its value is `true`, a message, or a non-empty set of messages. Unset, `outcomes` is `[deny]` and nothing changes.

```rego
package main

import rego.v1

# Rotating a launch template or a certificate is routine.
allow_unattended_routine if {
  every rc in input.resource_changes {
    rc.type in {"aws_launch_template", "aws_acm_certificate"}
  }
}

hold_iam contains msg if {
  some rc in input.resource_changes
  startswith(rc.type, "aws_iam_")
  rc.change.actions != ["no-op"]
  msg := sprintf("%s changes IAM", [rc.address])
}
```

Each wave combines its roots that change something:

| Rules matched | Wave |
|---|---|
| any `deny` | refused, unless an [override](#overriding-a-denial) stands |
| any `hold` | waits for an approval |
| an `allow_unattended` for every root that changes something, and no `hold` | applies without an approval, whatever `gate` says |
| otherwise | `gate` decides |

`cost.approve_above`, a hook with `onFailure: "approve"` and a root that read an output unknown at review still hold a wave the rules allow.

`outcomes` is read from the config at base, and with `hold` or `allow_unattended` in it `tf-apply` reads the policy itself at base too, so a pull request that adds an `allow_unattended` rule is decided by the base branch's rules. The pull request's plan note says what each wave will do and which rules decide it: "applies without an approval: allowed unattended by `main.allow_unattended_routine`", or "waits for an approval (held by `main.hold_iam`)". The job's log names each rule that held or released the wave, and the wave's report carries them in `waves[].policy_gate` with the commit the policy was read at, as does its `apply` entry in the [audit trail](/terragucci/reference/audit-trail/). Each root's report lists the rules it matched in `roots[].policy.held_by` and `roots[].policy.allowed_by`.

Test the rules as you test a denial: `tf-check` runs `opa test` on them.

## The base branch decides

A pull request's plan is checked against the `policy` key and directory at the base branch, so editing, deleting or renaming them, or `terragucci.yml`, changes nothing until merged.

| At the base | Result |
|---|---|
| no `policy` key | the pull request's own policy applies |
| the key, but no directory, or an unreadable config | every planned root fails |
| commit missing from the checkout | the checkout's key: every root fails if it has one, else no policy runs |

A base `terragucci.ts` is folded to a value without running it.

## Tests and the apply check

### tf-check

`tf-check` runs `conftest verify` or `opa test` on the base branch's policy and fails on a failing test. A directory with no `*_test.rego` is skipped.

### tf-apply

`tf-apply` checks each wave's plans before gating them. A denied wave applies nothing and records no approval; with `override` set it records the denial for an [override](#overriding-a-denial), and a root an override stands for goes on to the gate. The policy comes from the default branch, or from `TG_BASE` when set; with `hold` or `allow_unattended` in [`outcomes`](#holding-or-releasing-a-wave), from the base the approval mode is read at.

### The engines

terragucci downloads a missing engine once per job and refuses one whose SHA-256 differs from the pinned one.

| Engine | Packages read | Pinned version | `tf-check` runs |
|---|---|---|---|
| `conftest` | every package, unless `namespace` names one | 0.71.0 | `conftest verify` |
| `opa` | `main` and the packages one level under it, or `terraform.policies` and its packages with `input: hcp`, unless `namespace` names another | 1.21.1 | `opa test` |

Offline jobs need the engine installed; drift runs and provisional Terragrunt previews skip the check.

## HCP Terraform policy sets

With `input: hcp`, terragucci wraps each plan as HCP Terraform does, so the Rego of an HCP Terraform OPA policy set reads the paths it reads there:

```yaml
policy:
  engine: opa
  path: policies
  input: hcp
```

```rego
package terraform.policies.no_public_buckets

import rego.v1

deny contains msg if {
  some rc in input.plan.resource_changes
  rc.type == "aws_s3_bucket_public_access_block"
  rc.change.after.block_public_acls == false
  msg := sprintf("%s must block public ACLs (workspace %s)", [rc.address, input.run.workspace.name])
}
```

### The run fields

`input.plan` is the plan; `input.run` holds what terragucci knows of the run, in HCP Terraform's field names:

| Field | Value |
|---|---|
| `run.workspace.name`, `run.workspace.working_directory` | the root's path in the repo |
| `run.organization.name` | the repo's owner, from `<host>/<owner>/<name>` |
| `run.project.name` | the repo's name |
| `run.commit_sha` | the commit planned |
| `run.speculative` | `true` in `tf-plan`, `false` in a `tf-apply` wave |
| `run.message` | `pull request <n>` for a pull request's plan, else empty |
| `run.is_destroy`, `run.refresh_only` | `false` |
| `run.refresh` | `true` |
| `run.replace_addrs`, `run.target_addrs`, `run.workspace.tags` | empty lists |
| `run.variables` | empty |
| `run.cost_estimate.prior_monthly_cost`, `proposed_monthly_cost`, `delta_monthly_cost` | with `cost` set, the root's monthly cost before, after and the change, as decimal strings |

### policies.hcl

With `engine: opa` and `input: hcp`, terragucci runs each policy in the set's `policies.hcl` as HCP Terraform does:

```hcl
policy "no_public_buckets" {
  query             = "data.terraform.policies.no_public_buckets.deny"
  enforcement_level = "mandatory"
}

policy "owner_tags" {
  query             = "data.terraform.policies.owner_tags.deny"
  enforcement_level = "advisory"
}
```

Mandatory messages fail the root, as does a missing or unmatched `query` or an unknown level; advisory ones, the default, warn. A `hard-mandatory` policy fails the root too, and no [override](#hard-mandatory-rules) can pass it.

`namespace` keeps only the policies whose query is in that package.

Without `policies.hcl`, opa runs each package under `terraform.policies` as a policy. conftest ignores the file and treats every policy as mandatory.

The pinned OPA reads Rego 1.0, so older policies need `if` and `contains`. terragucci does not run Sentinel or `tfpolicy` policies.
