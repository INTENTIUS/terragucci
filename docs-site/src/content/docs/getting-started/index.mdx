## What you end up with

A pipeline file committed to your repo, and a pull request that carries one plan note from terragucci. The note groups the roots a change reaches and names every destroy.

[How terragucci works](/terragucci/concepts/how-it-works/) follows one change from pull request to drift and says what runs where. To see it work before touching your own repo, [the tutorial](/terragucci/tutorial/) runs a 15-root example on your laptop. A coding agent can also do these steps for you: [hand it this prompt](/terragucci/getting-started/agents/).

## Before you start

| You need | Why |
|---|---|
| a repo with Terraform, OpenTofu or Terragrunt roots, on GitHub, GitLab or Forgejo | terragucci reads the roots and the forge from the repo |
| Node.js 22 or later, on your machine only | `init` is an npm package; the pipeline itself runs in terragucci's CI image |
| a way for CI to read your state and providers | the plan job runs `plan`; [Environment variables and credentials](/terragucci/reference/environment/) shows OIDC roles and the variables a job reads |
| push access to the repo | you commit the generated pipeline |

## Steps

### 1. Install terragucci

From the root of the repo:

```bash
npm i -D @intentius/terragucci
```

### 2. Preview what it finds

```bash
npx terragucci init --dry-run
```

It writes nothing and prints what it found, with the reason for each choice:

```text
found 15 roots in 2 layers, tofu 1.13.1 (tofu on the path), forge github (the origin remote (github.com))
would write .github/workflows/terragucci.yml
would write chant.workspace.json
no terragucci.yml needed (defaults fit)
dry run: nothing was written
```

The roots are every directory that declares a backend or a `cloud` block, or configures a provider. A root on HCP Terraform with remote execution runs its plans on HCP Terraform's workers; [root](/terragucci/concepts/glossary/#root) says what that means for the jobs. The layers are the dependency order, read from `terraform_remote_state`. They are not the waves: `tf-apply` builds its [waves](/terragucci/concepts/glossary/#wave) from the layers, with any canary roots first. If the binary or the forge is wrong, pass `--binary` or `--forge`. `npx terragucci init --dry-run --json` lists the reason for every root.

### 3. Write the pipeline

```bash
npx terragucci init
```

```text
found 15 roots in 2 layers, tofu 1.13.1 (tofu on the path), forge github (the origin remote (github.com))
wrote .github/workflows/terragucci.yml
wrote chant.workspace.json
no terragucci.yml needed (defaults fit)
```

The file differs by forge. On GitLab it is `.gitlab-ci.yml`, and on Forgejo it is `.forgejo/workflows/terragucci.yml`. Open the file and read it once. Every job runs in terragucci's CI image for your binary. A job downloads a tool only if you pin a version the image lacks, which makes it run `terragucci install` first, or if you set a policy, which fetches conftest on first use.

[`chant.workspace.json`](/terragucci/concepts/glossary/#chantworkspacejson) declares the approval gate of each wave. Commit it with the pipeline: the apply job reads it from the default branch. A Terragrunt repo gets no such file.

Most repos need no `terragucci.yml`. When you do want one, [Your config file](/terragucci/reference/config/) lists every key.

### 4. Give the pipeline a token

GitHub and Forgejo jobs use the run's own token. On GitLab, add a project access token with the `api` scope as a masked CI/CD variable named `GITLAB_TOKEN`. The plan job uses it to post the note and the commit status.

### 5. Commit and open a pull request

```bash
git switch -c add-terragucci
git status
git add -A
git commit -m "Add terragucci"
git push -u origin add-terragucci
```

`git status` should show the pipeline file for your forge, `chant.workspace.json`, `package.json` and `package-lock.json`. Anything else, such as `node_modules`, belongs in `.gitignore`.

Open the pull request on your forge. The check and plan jobs start on their own. If the pull request touches no root, there is nothing to plan, so change a line in one root first and push again.

### 6. Read the plan note

When the plan job finishes, the pull request gets one comment and a `terragucci/plan` status. The note looks like this:

<PlanNote />

The note links to the full report, and every root in it links to its plan. [The plan report](/terragucci/reference/report/) shows what each part holds.

## Before your first approval

The plan note works without this. Approving a wave needs it, and a change that destroys something leaves a wave waiting. Approvals are sealed with an ssh key, so before the first one:

1. Install [chant](/terragucci/concepts/glossary/#chant) where you approve: `npm i -D @intentius/chant`.
2. Add your public key to `.chant/allowed_signers` through a reviewed pull request to the default branch, one line per person who approves. [Set up the signers file](/terragucci/guides/approve-a-wave/#set-up-the-signers-file) gives the format and the branch protection to set.

Without a listed key, a waiting wave has nobody who can approve it.
